# AGENTS.md — правила работы над sim-cs2 (для всех агентов: Claude Code, Codex, DeepSeek, ChatGPT)

Симулятор раундов CS2 на радаре (Ancient, Mirage; 10 ботов). Цель — боты играют и выглядят как про-игроки. Владелец — не
программист: оценивает глазами и по цифрам сравнения с демками про.

**Сейчас идёт перестройка (с 15.11):** всё по ней — папка `rebuild/` (правила этапа `rebuild/RULES.md` действуют поверх этого файла).

**Где что лежит:** план — `00_PLAN.md` · история версий и правил — `CHANGELOG.md` · принципы — `docs/PRINCIPLES.md` · устройство —
`docs/ARCHITECTURE.md` · решения — журнал по версиям `docs/DECISIONS.md`, действующие архитектурные (АР-) — `docs/architecture/DECISIONS.md` · правила правок, кода и прогонов — `docs/rules/` (`fixing.md`, `code.md`, `runs.md`).

---

**Начало любой сессии (Р0.9, 24.11):** `rebuild/JOURNAL.md` §2 «Сейчас» → раздел текущего этапа `rebuild/MASTER_PLAN.md` → только файлы,
названные в шаге. Команды — одна точка входа `node tools/sim.js help` (Windows и Linux одинаково). Агентам без доступа к репозиторию
(ChatGPT, DeepSeek в чате) владелец даёт пакет `node tools/sim.js context <тема>` — те же правила текстом.

**Как решать, писать ли код** (принципы Ponytail в адаптации проекта, `docs/architecture/DECISIONS.md` АР-16):
1. Нужен ли код вообще — может, это данные карты или пакета, а не код?
2. Есть ли хозяин этого решения — тогда строка (вариант с весом) у хозяина, а не новая функция рядом (§7).
3. Есть ли общий помощник (`nearP`, `taskProp`, события `simEvOn`, позже `dmath`, `KnowledgeView`) — взять его.
4. Только потом новый код — и старое удаляется в той же правке.
«Меньше кода» не значит «правка в месте симптома»: механика чинится во всех местах сразу (§5); проверки, безопасность и наблюдаемость не
урезаются.

**Graphify** (владелец 24.11): только локальный разбор исходного кода (`src/`, `tools/`); тексты документов во внешние API не отправлять
без согласия владельца; `graphify-out/` в git не кладётся. Граф — подсказка для навигации, правда о связях — `rebuild/gen/` (`gen_maps.js`).

## 1. Главный принцип игры
- Бот знает и делает то, что может знать и делать настоящий игрок в про-матче — не больше и не меньше (восприятие + тимспик + общая
  картина команды). Никаких правил под отдельную ситуацию и никакого «как у про» внутри мозга: демки — только для сверки.
- **Событие обновляет картину мира, а не назначает действие.** Факты / предположения с уверенностью / базовые знания — раздельно;
  бот моделирует и то, что знает о нём противник; действие — из картины мира, знаний и цели, одна общая система, а не правило на событие.
- **Семь обязательных требований к любому решению** (владелец 22.11; общая болезнь: неполный контекст → решение в отрыве от соседних
  систем → не пересматривается → нелогичный маршрут, граната, ротация, реакция):
  1. *Ничего не выкидывать молча* — значимый фактор, доступный другой системе, учитывается или явно объяснено, почему не влияет.
  2. *Решение по совокупности*, а не по одному порогу.
  3. *Системы связаны* — берут друг у друга нужные данные и возможности (граната ↔ движение, контакт ↔ пространство, сейв ↔ ретейк).
  4. *Пересмотр* — после значимого изменения ситуации решение и задача пересматриваются хозяином.
  5. *План исполняется* — выбранный план реально меняет маршруты, позиции, гранаты и действия игроков.
  6. *Только своё знание* — никакой информации, которой у игрока не было бы.
  7. *Путь, а не прямая* — перемещение и «успею» — по навигации.
- Подробно — начало `docs/PRINCIPLES.md`, `docs/PLAYER_MINDSET.md`.

## 2. Экономия лимита (обязательно)
Каждый шаг пересылает весь разговор заново — лишнее чтение дорого вдвойне.
- В начале чата ничего не читать «для контекста»: карты файлов §11 хватает (таблица «Где что» — `docs/ARCHITECTURE.md`, искать `grep -n`). Доки открывать, только когда задача их касается, и только
  нужный раздел: `grep -n` по слову → `Read` с offset/limit. `docs/archive/` — не открывать.
- Код — кусками: `grep -rn 'имя' engine view` → `Read` нужных строк. Файл целиком — только если он меньше ~150 строк.
- **Никогда не читать целиком:** `ancient-radar.html`, `mirage-radar.html`, `sim.html` (сборки, ~1–16 МБ), набор карты
  `data/maps/*/*.json` и `radar.png` (кроме `map.json` и нужного куска `tactics.json`), `navmesh.json`, `heights.json`, `zonemap.json`,
  `data/pro/*`, `data/demos/*`, `tools/measure/results/*`, `*.diff`, картинки.
- Не сканировать весь проект без прямой просьбы владельца. Вспомогательные агенты (если среда их даёт) — только с предупреждением
  владельцу и только с готовыми файлами / строками; код правит основной агент. Список своих агентов Claude Code — `CLAUDE.md`.
- Вывод команд — коротко (`| tail`, `| head`, `grep`); большие JSON / CSV и логи в разговор не печатать.
- Базу страницы (отметки, правки карты) забирать, только когда владелец просит или задача от неё зависит.

## 3. Порядок работы над задачей
1. **Ветка.** В начале чата — ветка `vNNN` от последней версии (номер — следующий после последнего в `CHANGELOG.md`). Правила веток — §4.
2. **Подтвердить понимание** — одним сообщением: «Понял так: … Это пункт XN или новый? Добавить?» + короткий план (что делаю, что
   удаляется взамен, какие цифры сдвинутся и куда, что может стать хуже). Ждать «да». Исключение — автономная работа (§10).
3. **Замечание владельца** — сразу пунктом в `00_PLAN.md`: ПЛАН (берём сейчас) или ДОРОЖНАЯ КАРТА (на потом), с датой и источником.
4. **Правка** — по правилам кода (§7) и правилам исправления ошибок (§5).
5. **Проверка** — §8 (снимок отметки / песочница / отпечаток / прогон на ПК).
6. **План и история:** сделал пункт — «сделано в vNNN (прогон N)» у пункта в `00_PLAN.md` («ждёт проверки» не пишем; повторилось у
   владельца — новый пункт с новой датой). Версия — одной строкой в `CHANGELOG.md`.
7. **Отчёт владельцу** — простыми словами: что сделано; «здоровье» кода было → стало (`python3 tools/health.py dist/sim.html`); честно — что
   не получилось и что не проверено.
8. **Конец задачи** (одна задача — один чат): `docs/ARCHITECTURE.md` — если менялось устройство; запись в `docs/DECISIONS.md` (держать
   3 последние, старые — в `docs/archive/` одной строкой); коммит; `00_PLAN.md`, `CLAUDE.md`, `CHANGELOG.md` — в `main` (§4).

## 4. Ветки, версии, план, changelog
- **Ветка = версия:** `v514`, `v515`, … — а не имя, которое выдала сессия (`claude/…`). Метки прогонов — тоже по версии (`v514_mir`,
  `v514_anc`). Ветки `claude/…`, `measure/…`, `pc-results/…` — служебные.
- **Буква в имени ветки = версия не закончена:** `v547` — всё, что в ней задумано, сделано и проверено, как требует план; `v547a`
  (альфа) — начата, сделано мало; `v547b` (бета) — основное сделано, есть недоделки. Доделали — новая ветка `v547` от той же точки
  (буквенную не удалять), в `CHANGELOG.md` — строка без буквы. Что не доделано в буквенной версии — пунктами в `00_PLAN.md`.
- **Планы — по одному на вид** (Р4.6, 26.11): перестройка до Р8 — `rebuild/MASTER_PLAN.md` (журнал — `rebuild/JOURNAL.md`); игра и поведение ботов — **`00_PLAN.md`** (корень). Две части `00_PLAN.md`: **ПЛАН** — ближайшее, работаем только по нему; **ДОРОЖНАЯ КАРТА** — будущее, туда
  сразу записывается каждая новая идея владельца (с датой). Внутри — подзаголовки по датам. Других планов нет (старые — `docs/archive/`, `rebuild/archive/`).
- **Все changelog'и — в `CHANGELOG.md`:** версии игры (одна строка: что, где опубликована, чем проверена), когда появились правила,
  с какой версии что устроено, ссылки на страницы. В `CLAUDE.md` историю не писать.
- **В `main` всегда лежат `00_PLAN.md`, `CLAUDE.md`, `CHANGELOG.md` и папка `rebuild/`** (документы перестройки, владелец 15.11): после правки любого из них — те же файлы одним коммитом в `main`
  (только они, без кода). Кроме списков сборки `rebuild/modules.json`, `files.json`, `owners.json`, `var_cats.json`, `state_classes.json` (реестр состояния, с Р3.1):
  их читает сборка, в `main` они следуют коду `main` (25.11: перенос `.ts`-списков сломал бы сборку `main` — исправлено 26197b0).
  Перенос — только `node tools/sim.js tomain [--push]` (владелец 25.11): итоговое дерево `main` собирается (обе карты, `gen_maps --check`)
  до пуша; чужие правки в `main` не перезаписываются — сначала забрать их в ветку (трёхстороннее слияние).
- Работа — только в своей ветке; не `main` (кроме трёх файлов выше), без force-push / `reset --hard`, без слияния и публикации без просьбы.

## 5. Как чинить ошибки игры (главнее остальных правил про правки)
**Перед любой правкой поведения — прочитать `docs/rules/fixing.md`** (полные правила владельца 09.11 / 18.11 / 22.11). Обязательно:
- **Механика, а не место:** найти ВСЕ места кода с той же механикой и исправить одной правкой у хозяина; в отчёте — список мест.
- **Все причины, от эпизодов:** счётчик → эпизоды (матч, раунд, тик, бот) → цепочка решения; не хватает данных — сначала диагностика.
- **Наборы A / B:** A — ошибочные эпизоды (обязаны исчезнуть), B — похожие правильные (сохраняются); воспроизвести со снимка до прогона.
- **Отметки владельца главнее цифр;** «как должно быть» — только как расписал владелец; видео «было / стало» (`tools/marks/mark_video.js`).
- **Запрет — только если действие невозможно** (физика, правила, ресурс), иначе вес в оценке; решение — по контексту, не по одному факту.
- **Не выдумывать причины:** «работает» — только после проверки на том самом случае; не проверил — «не проверено».

## 6. Откуда брать поведение и числа
- **Как играют про — из достоверных источников, не из головы:** сначала `docs/PRO_PLAY.md`; нет ответа — искать (HLTV, разборы тренеров,
  интервью про) и дописать туда со ссылкой; числа — из наших демок. Не «если X — делай Y»: у бота намерение из роли и плана, меняется
  по тому, что он знает. Цепочка решений про — `docs/PRO_DECISIONS.md`.
- **Придумывать как можно меньше:** каждое правило и число поведения — из демок, игры или источника. Нет нигде — своё, с пометкой
  «проектное число» в коде и в `DECISIONS.md` (первый кандидат на замену данными). Список — `grep -rn "проектное число" engine`.
- **Роли и места игроков — по картам:** есть демки этой карты с этими игроками — из демок (доля времени на позициях); нет — из интернета
  со ссылкой в `PRO_PLAY.md`; нет и там — так и писать, а не ставить по месту в составе молча.
- **Оформление страницы** — по репозиториям владельца (`docs/DESIGN_SOURCES.md`). Перед любой правкой вида — `DESIGN.md` (корень:
  цвета, шрифты, размеры, компоненты, движение), значения — оттуда; новое значение — сначала в `DESIGN.md` и токены `:root`.
  Проверка — снимки `tools/page/broadcast_shot.js`.

## 7. Правила кода
**Перед правкой кода — прочитать `docs/rules/code.md`** (полные правила). Обязательно:
- **Заменять, а не добавлять** — старое удаляется в той же правке. Новое условие — строкой **внутри функции-хозяина решения**
  (место — `setPost` / `TASK_LEVEL`; взгляд — `lookArbiter` / `LOOK_LEVEL`; ход — `engine/bot/move`; бой — `fightState`; урон —
  `applyDamage`; фаза плана T — `tPhaseSet`; остальные — таблица «Где что», `docs/ARCHITECTURE.md`).
- **Нельзя:** функция, пишущая поле бота мимо хозяина; свой замок `_xxxUntil`; проверка чужой задачи по имени (`taskProp`).
- **Устройство охраняет сборка** (`gen_maps --check`): хозяева полей, показ, модули, новые файлы, замки, дубли имён, общие переменные,
  истина врага (`rebuild/truth_known.json`), карточки механик (`rebuild/cards.json`). Упала — чинить код, не списки.
- **Математика расчёта — только `DM.*`**; путь, а не прямая («успею», «ближе», «дошёл» — по навмешу).
- Файл > ~600 строк — делить по смыслу у границы функций (`tools/rebuild/split_file.py`); новый файл — строка в `rebuild/files.json`.

## 8. Проверка и прогоны
**Перед проверкой или заказом прогона — прочитать `docs/rules/runs.md`** (полные правила). Обязательно:
- Правка не меняет игру → отпечаток бит в бит (`tools/measure/fingerprint.sh`), быстрый локатор `tools/measure/diverge.js`.
- **Облако — только короткие проверки; ПК (GitHub Runner) — Э1, массовые прогоны, замеры:** задание — `tools/measure/request.json` в ветке
  `measure/<имя>`, результаты — `pc-results/<N>`; одним заданием, `procguard`, `"resume": true`, Chromium `par` 8, Firefox ≤ 2; перед пушем —
  нет идущего / ждущего задания.
- База и правка — на одних 8 матчах каждой карты (3, 7, 11, 13, 17, 19, 23, 29); 2 матча — не проверка.
- **Метрика — не доказательство:** сначала достоверность детектора и эпизоды; не менять поведение ради счётчиков.

## 10. Долгая автономная работа
Полный текст — `docs/archive/OVERNIGHT_WORKFLOW.md`; задания — `docs/tasks/CLAUDE_*`, `docs/tasks/TEAM_UTILITY_EXECUTION_AND_DROPS.md`;
отчёты — `docs/reports/AI_BEHAVIOR_ROOT_CAUSE_AUDIT_34_ISSUES.md` (+ `evidence/`), `docs/reports/GRENADE_PHYSICS_ROOT_CAUSE_ANALYSIS.md`.
- Владелец дал задание на автономную работу — «подтвердить и ждать да» не нужно: обычные инженерные решения не спрашивать; поведение,
  которое владелец не расписал, — вопросом, и делать независимые пункты.
- Разделять: симптом (слова владельца) → путь в коде → воспроизведено (снимок / прогон) → гипотеза → предложение. Причина без проверки —
  гипотеза.
- Прогресс между сессиями — в `00_PLAN.md`; в новой сессии — сверить его с `git log`.
- Не ослаблять проверки ради зелёного результата; не подгонять лайнапы под неверную физику гранат; не давать ботам знание, которого у
  игрока не было бы.
- Задача заблокирована (нет отметки, источника, данных) — точную причину у пункта в `00_PLAN.md`, взять следующую независимую.
- Повторные прогоны «пока не заработает» — нельзя: одна гипотеза → одна правка → одна проверка.

## 11. Карта файлов
- **Набор карты:** игра не знает ни одной карты — всё про карту (зоны, навмеш, стены, высоты, укрытия, прострелы, тактики, лайнапы, места
  про, радар) лежит в `data/maps/<карта>/` и приходит в код одним объектом `MAP` (`docs/ARCHITECTURE.md`, «Набор карты»). В коде — никаких
  названий мест и координат: место карты — поле набора (свойство зоны или розыгрыш `tactics.plays`).
- **Сборка набора:** `python3 tools/map/map_build.py <карта>` по рецепту `data/maps/<карта>/_build.json` (навмеш из `.nav`, стены, высоты,
  укрытия, зоны по подписям радара — из демок; общий `tools/mapdir.py`). Ancient — заморожено всё, кроме высот / укрытий / прострелов.
  Подъёмы и прыжки через щель из демок — `tools/map/climbs_bake.py`, `tools/map/gaps_bake.py` (вручную; после них — пересчитать подбор гранат
  `tools/nades/guess_bake.py`). Проверка глазами — `tools/map/map_shot.js`.
- **Памятка данных карты** (владелец 17.11: «чтобы для новой карты всё бралось сразу»): что должно быть у каждой карты, для какой ситуации и
  чем делается — `tools/map/map_manifest.json`; проверка всех карт — `python3 tools/map/map_check.py` (новая карта — без «✗»).
- **Сборка игры:** `python3 src/build.py [--map ancient]` → `dist/sim.html` (склейка файлов игры по списку `rebuild/files.json` с набором карты и тестовым входом для замеров).
- **TypeScript (Р1, с 25.11):** файл игры может быть `.ts` — только стираемый синтаксис (`tsconfig.json`: strict, `erasableSyntaxOnly`);
