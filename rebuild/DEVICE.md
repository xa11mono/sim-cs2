# Устройство игры — черновик на согласование (фаза 2, 15.11.2026; ответы владельца 15.11 внесены)

Что это: как разложить мозг ботов по полочкам, чтобы правка одного не ломала другое. Цифры «сейчас» — из сгенерированных карт
(`rebuild/gen/`: `fields.md` — кто пишет поля, `tick.md` — порядок тика, `registry.md` — решения). **Боты от этого документа не
меняются**: всё, что ниже помечено «перенос», делается бит в бит; что помечено «поведение» — отдельной правкой с прогонами на ПК.

## 1. Каналы — кто за что отвечает

Канал — одно решение бота и один его хозяин. Внутри канала — свои правила; снаружи — только «предложить» и «прочитать».

| канал | решает | хозяин (функция, решает) | исполнитель | поля бота канала | пишут сейчас (функций) |
|---|---|---|---|---|---|
| **знание** | что бот знает о врагах и своих | `KNOW` / `knowTick`, войс `teamTick` | — | `know`, `belief` команды | (одно место с v240 / v266) |
| **место** | куда встать, задача, стойка (присед) | `setPost` / `TASK_LEVEL` | `updatePost` → путь | `post`, `_task`, `crouching` (владелец 15.11: присед — место) | `post` — 3, хозяин один ✓; `crouching` — 6 |
| **взгляд** | куда смотреть | `lookArbiter` / `LOOK_LEVEL` | `handTurn` (рука из демок, В147) | `facing` | `facing` — 9 функций, хозяина записи нет |
| **гранаты** | какую, кто, куда, когда | `teamNadePlan` / `npUse`, `nadeBrains` | `throwNade` / `lineupTick` | `nadeTask` | `nadeTask` — 11 функций |
| **бой** | стрелять, укрытие, режим, держать угол | `fightState`, `duelBalance` | `tryShoot`, `fightCycleTick` | `state`, `holding` (владелец 15.11: держит угол — бой) | `state` — 3 (хозяин `fightState`), `holding` — 6 |
| **ход** | шагом / бегом / стоять, путь | `moveWalkWhy` / `moveSpeedTick` | `stepTick` (физика шага) | `walking`, `curSpeed`, `path` | `walking` — 6, `curSpeed` — 9, `path` — 21 |
| раунд | закуп, бомба, конец раунда | `buyForPlayer`, `bombTick`, `endRound` | — | деньги, бомба | — |
| показ | экран, звук, войс-панель | — | — | — | (не пишет поля ботов — цель) |

Порядок переноса (фаза 3, согласован): **взгляд → место → гранаты → бой → ход**.

## 2. Тик — что сейчас и к чему идём

**Сейчас** (`tick.md`, по коду `stepTick`): мозги команд и гранат (`teamBrains`, `nadeBrains`, `updateNadeTasks`, `nadesTick`) →
по каждому боту: место, перезарядка, ход, пики взгляда, цикл перестрелки, лестницы → перестрелки целиком (`resolveEngagements`:
видимость, взгляд, выстрел) → знания в конце тика (`teamInfoTick`, `knowTick`, `teamTick`, `beliefTick`) → конец раунда, наблюдение.
То есть решения тика опираются на знания прошлого тика, а взгляд выбирается внутри перестрелок.

**Цель** — пять слоёв, каждый канал в каждом слое делает одно:

```
 1 знания      видимость, звук, войс, радар        → что каждый знает (из прошлого тика)
 2 намерения   каждый канал: кандидаты + причина + уровень (место / взгляд / гранаты / бой / ход)
 3 согласование хозяин поля выбирает одного (TASK_LEVEL, LOOK_LEVEL, …), пишет поле и причину
 4 исполнители рука (поворот), шаг, бросок, выстрел — только по выбранному
 5 физика      движение, полёт гранат, урон, конец раунда → 6 наблюдение (PROB, запись матча)
```

- **Перенос** (бит в бит): в `stepTick` — тот же порядок, но названными этапами (список этапов в одном месте; что из прошлого тика,
  что из текущего — подписано).
- **Поведение** (отдельно, с прогонами): переставить вызовы под пять слоёв (например, взгляд — до перестрелок). Это меняет игру.

## 3. Правило «поле пишет только хозяин» — как держим

- Карта писателей генерируется (`gen_maps.js` статически + `field_watch.js` живьём на ПК).
- Проверка сборки: запись поля перенесённого канала не из канала — **ошибка сборки**; до переноса — предупреждение со списком.
- Замки (`_xxxUntil`), проверки чужой задачи по имени — только внутри канала-хозяина.

### 3а. Интерфейсы между каналами — обязательная часть каждого шага переноса (владелец 15.11)

Канал переехал, а соседние ещё нет — старые файлы не пишут его поля, а зовут его интерфейс («просьба» с причиной; хозяин решает).
Иначе выйдет промежуточное устройство, где хозяин объявлен, а поле по-прежнему пишут все. Что заменит прямую запись сейчас
(`rebuild/gen/fields.md`):

| поле (канал) | кто пишет мимо хозяина | интерфейс |
|---|---|---|
| `facing` (взгляд) | `resolveEngagements`, `lookTrack`, `handTurn` (510), `freezeLookTick`, `stepTick` (540), `throwNadeTry` (380), разминка, демо, сброс | взгляд: «повернуть к» (цель, причина, уровень) → хозяин; рука `handTurn` — исполнитель внутри канала |
| `holding` (бой) | `moveSpeedTick` (535), `weaponPickupTick` (450), `resolveEngagements`, `leaveHold`, песочница, сброс | бой: «снять удержание» (причина) — ход и предметы просят, бой решает |
| `crouching` (место) | `duckDecide`, `resolveEngagements` (510), `fightCycleTick` (470), `moveSpeedTick` (535), `leaveHold`, сброс | место: «стойка» (присесть / встать, причина) — бой просит, место решает |
| все поля | сброс раунда (530), повтор клатча (675), песочница (677), демо (678), разминка (660) | у каждого канала — «сбросить» и «восстановить из снимка»: они пишут его поля только так |

Генератор различает объекты: `bot.state` ≠ `bomb.state` ≠ состояние редактора (то же имя поля у бомбы, смока выхода, повтора —
отдельно, в проверку владения не идёт). Строгая ошибка сборки включается только после этого разделения (сделано 15.11).

## 4. Модули — вариант А (владелец 15.11)

Факт: общих переменных 886, из них **101 пишут из чужих файлов**. Решено: сейчас — свои проверки по склейке, модули — по каналу в
фазе 3 (канал переехал → его состояние у него → он модуль, esbuild, отпечаток бит в бит). С уточнениями (владелец 15.11):
- **не раскладывать всё по объектам каналов.** У каждой общей переменной — категория по смыслу: канал / мир (карта, навмеш, гранаты
  в воздухе, предметы) / раунд (часы, состояние раунда, бомба, матч, деньги) / кэш / временное / показ. Хозяин — по смыслу, не по
  файлу. Таблица — `rebuild/gen/vars.md` (категории — `rebuild/var_cats.json`): показ 38, мир 24, раунд 16, канал 15, кэш 7, временное 1.
- больше всего чужих записей — сброс раунда (`530`) и повтор клатча (`675`, восстанавливает состояние): им нужен интерфейс
  «сбросить / восстановить» у хозяина, а не запись в чужие переменные (§3а).

## 5. Показ отдельно от симуляции

Экран из симуляции трогают `440` (войс-панель), `495` (хайлайты), `530` (раунд). Перенос: симуляция пишет события («раунд кончился»,
«фраза в войс»), показ их читает. Игра не меняется (бит в бит), а замеры на ПК не зависят от экрана.

## 6. Разбор решения — одна цепочка для любого канала

Сейчас: разбор взгляда (`LOOKDBG`), журнал решений (`645_decision_log`), причины хода (`_walkWhy`). Цель — у каждого хозяина одна
запись: **знал → варианты → почему этот → кто разрешил / перебил → кто выполнил → что вышло**. Читается и на странице (галочка), и
по записям матча (`rec2.js`), и по снимку отметки — тем, кто разбирает ошибку (RULES п. 5–6: найдено / исправлено).

## 7. Счётчики и проверки по отметкам

- Каждый прогон на ПК — одна таблица «было / стало» (застревания, переносы, смерти к 20 с, длина раундов, планты, гранаты, взгляд,
  покрытие входов CT), красное видно сразу (`check.py` → одна страница).
- Отметки владельца — сценарии: снимок + вопрос «да / нет» («бот держит угол X?»); прогоняются после каждой правки поведения.
