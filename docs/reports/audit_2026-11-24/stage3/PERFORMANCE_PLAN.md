## 2. Кандидаты (в порядке пользы)

Частота — `evidence/call_counts_mir_m3.json` (Mirage м3, 12 000 тиков с начала раунда, 9 440 живых). Доля времени — включительное время из
профиля этапа 1 (Ancient / Mirage). «Повторы» — тот же запрос (те же точки, округлённые до 1 ед.; для пути — откуда/куда/сторона/шаг) в том же
тике и в окне 32 тиков.

### К-1. Поиск пути — `050_nav_rebuild_paths.js`: `zoneDijkstra`, `buildWaypointPath0`, `funnel`, `knownSegCost`; `100_sites_spots.js`: `pathQ`, `pathPts`, `pathLenTo` (180)

| что | значение |
|---|---|
| частота | `zoneDijkstra` 3,7 / тик, `funnel` 5,3, `knownSegCost` 716, `pathQ` 72, `pathPts` 58, `pathLenTo` 10 / тик |
| доля времени | 35 % / 40 % `stepTick` (включительно); собственное — `relax` 20 / 41 с, `zoneDijkstra`, `dist2`, `makeHeap` |
| вклад в пики | П-02 (1,56 с — `nadeThrowSpot` → `luBehind` → 3 поиска на кандидата); П-06 (первый тик раунда) |
| повторы | **51 %** запросов повторяют тот же запрос в окне 32 тиков, 6 % — в том же тике (кэш дерева поиска на тик `ZDJ` уже есть, 050:423–426) |
| структуры | граф — массивы рёбер `{to, mid}` в объекте по id; поиск — объекты `dist/prev/visited/entry` со строковыми ключами, куча из объектов |
| глобальное состояние | `zoneGraph`, `zonesById`, `fires`, `knownPathSpots(team)` (знание команды), `tick`, `matchNum`, свойства функции `zoneDijkstra.quiet/fire/from/toPt/nearest` (параметры через свойства функции!) |
| эталон | та же логика: объекты 814 мкс/запрос → массивы **302** → Rust нативно 141 → Rust WASM 245–262 (`evidence/bench_results.md`) |
| передача JS ↔ WASM | 0,7 мкс на вызов; граф (~8 тыс. рёбер) передаётся один раз; на каждый запрос — список мест врагов (≤ 10 точек) |
| риск поведения | порядок выбора при равной стоимости и биты `hypot` (Rust ≠ JS в 384 / 3000) — без общей математики перенос не бит в бит |
| параллельность | внутри матча — нет смысла (3,7 / тик); между матчами — да |

**Решение: E сейчас, D — опция R6.**
1. Параметры `zoneDijkstra` — аргументом, а не свойствами функции (архитектура, бит в бит).
2. Граф и поиск — плотные массивы (`Int32Array/Float64Array`, индексная куча) — бит в бит, если сохранить порядок обхода рёбер и правило равенства.
3. Кэш результата поиска по ключу «откуда/куда/сторона/шаг/версия знания команды/версия огня» на время, пока версия знания не меняется (51 %
   повторов — верхняя граница выигрыша); ключ из версий, а не из TTL — иначе поменяется поведение.
4. `nadeThrowSpot` — место броска один раз на задание (П-02).
5. Только если после 1–4 доля пути > 30 % — Rust-ядро (R6).

## 3. Где что выполнять

| компонент | где | почему |
|---|---|---|
| симуляция матча (весь `stepTick` и его зависимости, 000–545) | **Web Worker** в странице; **Node** `worker_threads` для замеров / массовых матчей | снимает блокировку интерфейса (проблема 2); один код |
| отрисовка 2D/3D, HUD, обсервер, звук, повтор клатча | **главный поток** | работает с DOM / WebGL; читает снимок состояния |
| редакторы карты (550–610) | главный поток; правка → сообщение в Worker → `rebuildNav` там | редактор не пишет в мир симуляции напрямую |
| отметки (`src/marks.js`) | снимок — команда Worker'у («отдай состояние»), хранение — главный поток | состояние живёт в Worker'е |
| поиск пути / лучи — Rust | только после R4 и только если нужно (R6): WASM в Worker, N-API в Node | одно крейт-ядро |
| параллельно | **между матчами** (по Worker'у / потоку на матч); внутри матча — нет (детерминизм и малые задачи) | |

**Открыть любой из параллельных матчей без копии визуального движка:** каждый матч — Worker / поток, который по запросу отдаёт **кадр
состояния** (позиции, взгляд, HP, гранаты, события — то, что сейчас читает `draw`). Один показ подписывается на кадры выбранного матча. Объём
кадра не мерился — замер в R3 (`postMessage` структурированного клона против `SharedArrayBuffer` с плоским массивом); решение — по замеру.

## 4. Как мерить «до / после» на каждом шаге

| шаг | обязательно | порог |
|---|---|---|
| правка без смены поведения (E, F, перенос на TS) | отпечаток 6 матчей (3, 7, 11 × 2 карты) бит в бит; `bench/cnt.js` | отпечаток равен; время тика не хуже базы (среднее и p99 на тех же тиках) |
| правка пиков (К-3, К-6) | окна Р-01…Р-06 (`../TEST_COVERAGE_PLAN.md` §5) | тик в окне ≤ 4 × бюджет (62,5 мс) — порог проверки, не цель качества |
| Rust-ядро (R6) | сравнение результата ядра с JS на 3000+ реальных запросах бит в бит; отпечаток матчей | 0 расхождений |
| массовая симуляция | матчей в час на ПК владельца, Chromium против Node | замер, без порога (база ещё не снята) |

Целевые числа для ПК владельца **не назначаются** без базы с его ПК: первый шаг R0 — снять базу этими же скриптами там.
