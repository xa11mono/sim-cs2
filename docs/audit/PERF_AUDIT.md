# Аудит производительности sim-cs2 (23.11.2026)

Замеры — облако, Mirage, матч 7, 12 000 тиков (~3 раунда), сборка `audit/postplant` (= `audit/all` + пост-плант T).
Инструменты (в `docs/audit/tools/`): `cpuprof3.js` (профиль, своё и полное время функций), `costby.js` (кто и сколько раз зовёт
поиск пути / подбор гранаты, время каждого вызова, распределение тиков), `djstat.js` (сколько участков раскрывает поиск).
Облако медленнее ПК, но доли — те же. На ПК метрика — «долгие тики» сторожа (`slow` в rec2).

## 1. Картина

- Средний тик — **8,4 мс** (64 тика в секунду игры = 540 мс на секунду игры при 1 боте-«сервере»).
- Тики: < 2 мс — 36 %, 2–5 мс — 21 %, 5–16 мс — 29 %, **16–50 мс — 13 %, 50–200 мс — 2 %, > 200 мс — 7 штук**.
- Куда уходит время (полное, с вложенными вызовами):

| что | доля | комментарий |
|---|---|---|
| **поиск пути** (`buildWaypointPath`) | **54 %** | 50 138 вызовов, 1,09 мс в среднем; из них сам граф-поиск (`zoneDijkstra`) — 37 % |
| система взгляда (`lookTick`) | 38 % | из них ~30 % — её же поиски пути (ниже) |
| видимость (`m3Cast` / `visLine` / `hasLOS`) | 13–15 % | ~250 лучей на тик |
| мозги команд (`tBrain`, `ctBrain`) | 23 % | в основном — их поиски пути |
| подбор броска гранаты (`nadeSolve`) | 2 % | но **65–85 мс на вызов** — это и есть долгие тики на ПК («smoke / flash / molly / he» в `slow`) |

## 3. Почему один поиск дорогой

1. **Обычная Дейкстра без направленности (без A\*)**: из 2 544 участков навмеша поиск раскрывает обычно **1 000–2 544** — почти всю
   карту, даже когда цель в 300 единицах (`djstat.js`: 63 % поисков — больше 1 000 участков).
2. Расстояния, «откуда пришли», «раскрыт» — **обычные объекты JS с ключами-номерами** (`dist[edge.to]`), куча — общая; на каждый
   переход — `dist2` (корень), `navJumpCost`, проверки огня и мест врагов.
3. **Пути без команды** (только карта; ~75 % вызовов `zoneDijkstra`) кэшируются по **точным координатам** — у идущего бота они
   меняются каждый тик, кэш почти не попадает.
4. **Пути команды** (с опасностью по знанию, 040) не кэшируются совсем (кроме продолжения поиска из того же начала в том же тике).
5. После поиска — `funnel` и `laneShift` (сдвиг по полосе проверяет пол через каждые 8 ед. — `navAt` + `pointInPoly`).

## 4. Что делать — по порядку выгоды и риска

Правило проекта: правка только скорости — **бит в бит** (отпечаток `fingerprint.sh` / позиции всех ботов), без прогона; правка, меняющая
числа решений хоть на сотую, — это изменение игры: прогон на ПК и согласие владельца. Физику гранат, 64 Гц и точность навмеша не трогаем.

### A. Без изменения игры (бит в бит)

| # | что | где | ожидаемо |
|---|---|---|---|
| A1 | Дейкстра на типизированных массивах: номер участка → индекс, `dist`/`prev`/`visited`/`entry` — `Float64Array`/`Int32Array`, куча на массивах, статичная часть цены перехода (`navJumpCost` для обоих режимов шага, `ROUTE_PORTAL`) — посчитана заранее на ребро. Порядок сложений и раскрытия тот же | 050 `zoneDijkstra`, `makeHeap` | Дейкстра в 2–3 раза быстрее → **−20…25 % всего** |
| A2 | Кэш видимости между **неподвижными** точками (места `pickSpots`, входы `threatEntrances`, порталы `portalWatched`, места пост-планта `holdTac`): геометрия не меняется, дым — отдельно (`smokeBlocks` не кэшировать) | 040 / 100 / 260 / 280 | −3…5 % |
| A3 | `laneShift`: проверка пола по отрезку (`navSegNoDrop` / `navSegOnLevel`) — кэш по отрезку (точки — середины переходов, повторяются) | 050 | −2…3 % |
| A4 | Повторы в одном тике: одна и та же длина «бот → точка» из разных систем (взгляд, шаг, ретейк) — память на тик по точным аргументам и версии знания команды | 050 `pathPts` / `pathLenTo` | −2…5 % |

**Итого A: ~25–35 % быстрее, игра та же.** Проверка — отпечаток бит в бит на 2–3 матчах в облаке, затем 8 матчей на ПК (совпадение с прошлым прогоном той же версии).

## 5. Предлагаемый порядок

1. **A1 → A2 → A3 → A4**, каждая — отпечаток бит в бит (облако), потом один прогон ПК на всё A (должен совпасть с прошлой версией бит в бит
   и показать меньше долгих тиков).
2. **C1** (пики гранат) — отдельной правкой с прогоном.
3. **B2 + B3** — вместе, с прогоном 16 матчей Mirage (сверка: решения «успею», колл, ретейк — те же цифры в пределах шума).
4. **B1** — последним, с проверкой совпадения путей на снимках.

Ожидаемо после всего: тик **в 2–3 раза быстрее**, долгие тики на ПК — в разы меньше.
