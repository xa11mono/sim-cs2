# Отметки владельца в sim-cs2

## Назначение

Отметка — это не просто текстовая жалоба. Это зафиксированный игровой эпизод с матчем, раундом, тиком, ботом, описанием ожидаемого поведения и снимками состояния. Используй отметки как первичный источник конкретных примеров владельца.

## Когда запускать этот навык

Запускай этот процесс автоматически, без просьбы владельца назвать ID отметки, когда:
- владелец говорит «отметка», «отметил», «посмотри мой момент», «как в том раунде», «проверь исправление»;
- задача по игровой логике соответствует симптому, который мог быть отмечен ранее;
- владелец просит проверить, что конкретная ошибка больше не возникает.

Не загружай все снимки без причины. Сначала найди подходящие записи по тексту, категории, карте, боту и статусу; скачивай снимки только для релевантных отметок.

## Источник данных

Отметки хранятся в браузере владельца: `localStorage` страницы под ключом **`sim_marks`** — JSON-массив записей. Базы страницы (`claude.use("db")`) и вложений (`claude.use("assets")`) у отметок больше нет (изменено 23.11, `src/marks.js`).

Поля записи: `id`, `match`, `round`, `roundTime`, `tick`, `category`, `priority`, `text`, `want`, `bot`, `status`, `version`, `fp`, `state`, `created`, `updated`, а также два снимка — `snap` (момент отметки) и `pre` (за 15 с до, может отсутствовать) плюс `preTick`. Снимки лежат **строками** в записи: это упакованный `mkPack` текст — ровно тот формат, который принимает `mark_open.js`. Картинок («кадр», «экран») в отметке нет — они не хранятся.

Статусы в интерфейсе: `new`, `unparsed`, `added`, `fixed`, `confirmed`.

## Как достать отметки (локальный браузер владельца, без серверов)

Владелец ставит отметку в игре (клавиша `M`) — она сразу пишется в `localStorage` его браузера. Агент забирает её сам через Playwright, ничего у владельца не скачивая.

1. Собрать страницу, если её нет: `python3 src/build.py` → `sim.html`.
2. Запустить сбор отметок (браузер владельца лучше закрыть — профиль блокируется, пока он открыт):

```bash
python tools/marks/mark_pull.py --profile "%LOCALAPPDATA%/Microsoft/Edge/User Data"
python tools/marks/mark_pull.py --profile "%LOCALAPPDATA%/Google/Chrome/User Data" --url "file:///C:/Projects/sim-cs2/sim.html"
```

Если браузер закрывать нельзя — запустить его с `--remote-debugging-port=9222` и подключиться:

```bash
python tools/marks/mark_pull.py --cdp http://127.0.0.1:9222
```

Скрипт кладёт `<out>/marks.json` и `<out>/<id>/{record.json,snap.json,pre.json}` (по умолчанию `tools/marks/inbox/`). Отметки привязаны к адресу страницы: `file://` и опубликованная страница — разные хранилища, поэтому `--url` должен совпадать с тем адресом, где владелец ставил отметку.

3. Дальше — обычные инструменты: `mark_open.js`, `mark_story.js`, `mark_frames.js`, `mark_video.js` (им нужен Playwright для Node: `npm i playwright` или `npx playwright`, плюс браузеры).

Ручной путь, если профиль недоступен: владелец один раз выполняет в консоли страницы `copy(localStorage.getItem('sim_marks'))` и присылает JSON — это допустимая замена, но не выдумывай содержимое отметок, снимков или их результаты.


## Локальный формат

```text
tools/marks/inbox/
  marks.json            # весь массив sim_marks как есть
  <mark-id>/
    record.json         # запись без snap/pre
    snap.json           # упакованный снимок момента (как лежит в записи)
    pre.json            # снимок «до», если он есть
```

`record.json` сохраняет исходные поля отметки и её `id`. `snap.json` и `pre.json` — **упакованный текст без пересборки и нормализации**: именно его принимает `mark_open.js` (`mkOpenSnap` распаковывает сам). В самой записи `snap`/`pre` лежат **сжатыми** (`gz:` + base64 gzip) — `mark_pull.py` распаковывает их при выгрузке. Не перезаписывай и не удаляй исходные записи в localStorage владельца — это его данные.

**Место в браузере.** Снимок одной отметки — около 1 МБ в base64 даже после сжатия, а квота localStorage ~5 МБ на страницу, то есть влезает 4–5 отметок. Поэтому после разбора забирай их с `--clear` (файлы в `tools/marks/inbox/` остаются) или почаще выгружай. Если места не хватило, `src/marks.js` сам снимает сначала `pre` у самой тяжёлой отметки, потом `snap`, потом удаляет самую старую — и показывает об этом сообщение в интерфейсе.


## Разбор одной отметки

1. Найди нужную запись в `marks.json` (или в `<mark-id>/record.json`). Покажи владельцу: карту, матч, раунд, время раунда, тик, бота, категорию, приоритет, текст проблемы и `want` (ожидаемое поведение).
2. Определи версию симулятора, которой соответствует отметка. Используй `version`, `fp`, дату отметки, `CHANGELOG.md` и соответствующий билд. Не считай текущую сборку эквивалентной автоматически.
3. Если есть `pre.json` и `snap.json`, запускай историю от `pre.json` до `tick`:

```bash
node tools/marks/mark_story.js <sim.html> <pre.json> <snap.json> [bot-id] > <report.txt>
```

Этот инструмент проигрывает примерно 15 секунд до отметки до нужного тика и сверяет итоговые позиции/HP/живых игроков со снимком отметки. Прочитай предупреждение о несовпадении. Если сверка не сошлась, это не точное воспроизведение; не объявляй причину доказанной.

4. Для самого состояния отметки без истории используй:

```bash
node tools/marks/mark_open.js <sim.html> <snap.json> "<JS expression>"
```

`mark_open.js` открывает снимок момента. Сам по себе этот снимок уже содержит решения, принятые до момента отметки; он не пересчитывает историю новым кодом.

5. Для визуального разбора по необходимости:

```bash
node tools/marks/mark_frames.js <sim.html> <pre.json> <snap.json> <bot-id> <output-dir>
node tools/marks/mark_video.js <sim.html> <pre.json> <tick> <bot-id> <from-sec> <to-sec> <output.mp4>
```

Проверь наличие Playwright/Chromium и ffmpeg. Видео/кадры — доказательство для визуального просмотра, а не замена сверке снимка.

6. Разделяй выводы по уровню доказательства:
- **по снимку видно** — факт из состояния отметки;
- **в истории подтверждено** — цепочка видна при воспроизведении и конечное состояние совпало;
- **гипотеза** — механизм в коде способен объяснить симптом, но эпизод не подтвердил его;
- **не проверено** — нет нужного снимка, версия не совпала, сценарий не возник или инструмент завершился ошибкой.

Если `pre.json` отсутствует, не заявляй, что причина или исправление подтверждены воспроизведением. Можно разобрать только зафиксированное состояние.

## Проверка исправления

1. Сначала зафиксируй базовое поведение на сборке версии отметки. По возможности воспроизведи тот же путь от `pre.json` до `tick` и сверь отпечаток/позиции/HP. Если старая версия не воспроизводит отметку, останови причинный вывод.
2. До изменения кода найди все эпизоды набора A (ошибочные случаи) и набора B (похожие, но правильные случаи). Не исправляй только конкретную координату/бота/раунд; чини механику у её хозяина согласно `CLAUDE.md` и `rebuild/RULES.md`.
3. После исправления повтори A и B на новой сборке. Для устойчивого регрессионного теста добавь сценарий в `rebuild/scenarios.json` только по правилам проекта и после согласования ожидаемого поведения владельцем.
4. Запуск проверки:

```bash
node tools/marks/scenarios.js --only=<scenario-id> --sim=<sim.html>
```

Сценарий использует `pre` + `tick` для пересчёта до отметки, затем `steps`, `when` и `check`. `when` может вернуть «ситуация не возникла» — это пропуск, а не успешное исправление. Код возврата `1` означает, что есть несовпадение или ошибка.

5. Если новая версия расходится с отмеченной до момента ошибки, не сравнивай видео из разных игровых состояний. Следуй `CLAUDE.md`: обе версии должны стартовать с одного состояния старой версии примерно за 2–4 секунды до проблемы.
6. Не меняй статус отметки на `fixed` или `confirmed` самостоятельно. Не закрывай отметку без результата A/B и требуемой проверки владельца.

## Отчёт владельцу

Пиши по-русски и простыми словами. Для каждой релевантной отметки укажи:

- ID и координаты эпизода: карта / матч / раунд / тик / бот;
- что владелец наблюдал и что ожидал;
- что именно показал снимок;
- сошлась ли история `pre → tick` с `snap`;
- подтверждённая причина либо гипотеза/ограничение;
- что должно измениться после правки;
- какие правильные сценарии B надо сохранить;
- что фактически проверено и что ещё не проверено.

Не говори «подтверждено», «исправлено» или «работает», если не воспроизвёл именно отмеченный случай и не проверил сохранение B.

## Правила проекта выше этого навыка

`CLAUDE.md`, `rebuild/RULES.md`, `docs/tasks/work_rules.md`, `docs/PLAYER_MINDSET.md` и прямые указания владельца имеют приоритет. Соблюдай правила веток, сначала диагностика, одна задача — один хозяин решения, без слияния/публикации без просьбы владельца. Не запускай полный прогон на ПК без соответствующего задания и согласованного плана.
