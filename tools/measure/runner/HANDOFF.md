# Прототип снижения памяти раннера замеров

База — `v599a` на коммите `da44c5648e6c9616ecbec9dd180a1daec6e0f403`. Точка запуска на ПК — `.github/workflows/measure.yml` → `tools/measure/remote_run.py` → `tools/measure/engine/walk_run.py` → `src/q.js`. Прототип для очереди `jobs` включается явно. Ветка задачи — `codex/lightweight-runner-prototype`.

## Результат короткой проверки

Linux, Node 24.22.3, Playwright 1.63.0, Chrome Headless Shell 158.0.8127.36. Матчи с номерами 3, 7 и 11 на каждой карте, по 1600 тиков, одновременно два. Замеряется пик **PSS дерева процессов раннера**, включая Python, Node и Chromium. PSS пропорционально учитывает общие страницы памяти. Время включает запуск, загрузку, запись и ожидание очереди.

| Карта | Старый раннер | Общий браузер | Общий браузер и запись частями | Дополнительно облегчённая страница |
|---|---:|---:|---:|---:|
| Ancient, пик МиБ | 1191,4 | 1064,7 | 1054,4 | **1033,6 (−13,2%)** |
| Mirage, пик МиБ | 1125,5 | 1008,7 | 995,8 | **962,4 (−14,5%)** |
| Ancient, секунды | 18,08 | 17,24 | 17,17 | 17,27 |
| Mirage, секунды | 18,23 | 16,29 | 16,17 | 17,18 |

Одна серия на конфигурацию. Сравнение полных JSON всех шести случаев совпало по каждому полю, кроме `slow`, которое записывает фактические медленные тики и их длительность. Оно присутствует в обеих записях и проверяется как метрика производительности. На выборке были убийства, броски, попадания и смены задач. Дополнительная проверка `fingerprint.js` сравнила результат исходного `src/q.js` и трёх новых режимов побайтно за 1600 тиков матча 11. Итоговые хэши — `1409138115` для Ancient и `3320052319` для Mirage. Проверка на синтетической записи также сравнила JSON побайтно при нескольких пакетах передачи, в том числе с кириллицей и Unicode. Параллельные и последовательные контексты прошли проверку изоляции `localStorage` и глобальных переменных страницы. После завершения всех четырёх режимов живых потомков среди наблюдавшихся процессов не осталось. Обычное завершение, таймаут и отмена очереди покрыты тестами.

Замер с восемью матчами и полной длительностью на Windows остаётся этапом приёмки. Показание Диспетчера задач для процесса, системный итог 12,1 ГБ и измерение PSS дерева на Linux используют разные границы. Выигрыш на ПК следует измерить отдельно.

## Где находится память

[Разбивка памяти, дублирование и приёмка Windows при par=8](MEMORY_BREAKDOWN.md).

| Компонент | Что видно в проверке |
|---|---|
| Браузер, Node и служебные процессы | Для Ancient при пике два основных процесса браузера занимали 62 МиБ PSS суммарно, с общим браузером — 45 МиБ. Python и Node вместе сократились с 202 до 117 МиБ. У GPU/utility/zygote также есть экономия. |
| Рендереры | Ancient — 787 МиБ PSS суммарно в старом режиме, 795 МиБ с общим браузером, 765 МиБ в полном прототипе. Mirage — 720, 735 и 700 МиБ соответственно. Рендереры и их V8-кучи остаются основным потребителем. |
| 3D-геометрия | `map3d.json` — 9,36 МиБ Ancient и 1,99 МиБ Mirage. CDP и отдельная проверка показали, что `MAP3D` ссылается на `MAP.map3d`, а `m3()` создаёт распакованные буферы внутри страницы. Сумма уникальных backing store `M3` для матча 3 выросла с 59,1 до 88,5 МиБ на Ancient и с 22,3 до 35,2 МиБ на Mirage. Геометрия нужна видимости, этажам, столкновениям и физике гранат. |
| Навмеш | Исходники — 249 КиБ Ancient и 420 КиБ Mirage. В странице есть исходный `MAP.navmesh.areas`, копия `NAVAREAS_RAW`, преобразованные `NAVAREAS`, `zoneGraph` и индексы. Подтверждены 1970 и 2544 области соответственно. Это обычные JS-объекты. После 1600 тиков сериализация графа занимала 856 КиБ на Ancient и 1213 КиБ на Mirage. Эти числа отражают объём записанных данных. Объекты и ссылки в куче имеют другой размер. |
| Кэши | За 1600 тиков матча 3 `WPM.n` вырос с 79 до 365 на Ancient и со 122 до 720 на Mirage. Лимит и сброс остаются действующими. `ZDJ` обновляет таблицу по тику и графу, `KPC` держит текущий результат по командам. Сериализация `WPM` выросла примерно с 16 до 105 КиБ на Ancient и с 23 до 278 КиБ на Mirage. |
| Диагностика | Наблюдатели и `REC` живут до закрытия контекста. Удаление опубликованной ссылки на `REC` после записи почти не изменило живую кучу в коротком замере. Функции подписок и другие ссылки из страницы продолжают удерживать данные до закрытия контекста. |

Метрики CDP и PSS перекрываются и не складываются. Для Ancient использованная V8-куча после принудительного GC выросла примерно с 31 до 43 МиБ, а внешние backing store с 81 до 113 МиБ. Для Mirage соответственно с 28 до 38 и с 33 до 46 МиБ. Рост включает разогрев игры, кэшей и наблюдателей. Контроль с теми же матчем и тиками без наблюдателей показал около 0,74 МиБ разницы живой JS-кучи после GC на каждой карте. Внешние backing store совпали до показанной точности. Это разница всего профиля с наблюдением на коротком входе. Рост записи длинного матча и режима снимков этим числом не измерен.

## Устройство и границы

- Один Node-брокер и один Chromium на очередь. Каждый матч получает новый `BrowserContext` и новую страницу. После выполнения контекст закрывается до публикации результата. При потере Chromium следующее задание запускает новый браузер, а ошибки текущих записываются как ошибки. Старая очередь и новая используют один и тот же код загрузки страницы и остановки кадра.
- `stream_records` сохраняет формат `rec_*.json`. Запись идёт через временный файл и завершается атомарным переименованием. Транспорт последовательно читает части объекта `REC`, включая массивы и словарь снимков, сохраняя число проверок, порядок и значения. Полный `REC` всё ещё хранится в странице до конца матча. Python по-прежнему отделяет снимки раундов после записи. Потоковая выдача **во время тиков** потребует точки безопасной передачи между батчами и согласования времени жизни объектов с аудитом Р3.
- `light_page` обрабатывает копию уже собранного HTML. Она заменяет фоновый PNG радара на пиксель и очищает таблицу портретов. Разметка, данные карты, геометрия, навигация, физика, сторожа и шаг симуляции остаются исходными. Размер HTML Ancient 14 741 619 → 14 086 139 байт, Mirage 8 628 110 → 7 870 346 байт. Для этого преобразования требуется распознаваемый формат тестовой страницы. Снимки экрана и визуальные режимы используют свою обычную сборку.
- Общий Chromium переиспользует браузерную инфраструктуру, но разные контексты имеют свои объекты `MAP`, `M3` и графы. Дедупликацию между матчами следует делать после выделения неизменяемых пакетов и отделения состояния матча на Р3/Р5. Общий буфер для геометрии возможен для исходных массивов только после проверки мутаций и битового совпадения. Рабочие штампы обхода, граф после правок карты, навигационные кэши и накопители остаются локальными для матча.
- В базе `da44c5648` и проверенных путях `src/`, `tools/measure/` и `.github/` идентификатор `FAST_MEASURE` не найден. Оба раннера наследуют окружение. Если существующий `FAST_MEASURE` находится в другой ветке, его следует передавать прежним способом и сравнить старую и общую очередь на одной сборке с тем же флагом. Новые параметры выбирают топологию процессов, транспорт результата и ресурсы страницы.
- Прототип включён для `jobs`, в том числе использует их существующую подготовку скриптов со снимками и переигровкой. Замеры `fp`, `cov`, снимки экрана и отдельные инварианты идут по своим прежним маршрутам. Натурная проверка была на обычных `jobs`. Режимы записи/переигровки снимков ещё требуют парного прогона на историческом корпусе.

## Воспроизведение

Для обоих запусков использовать одинаковые браузер, Node, ref, карту, список матчей, тики и `par`. Диагностический CLI симуляции требует штатного Playwright. Для выборки дерева процессов `compare.py` отдельно нужен `psutil`. Windows по умолчанию измеряет USS, Linux — PSS. Для суммы рабочих наборов можно явно передать `--metric=rss`, с учётом повторного подсчёта общих страниц.

```sh
node --test tools/measure/runner/runner.test.cjs
python -m unittest discover -s tools/measure/runner -p "test_*.py"
python src/build.py --map ancient ancient-test.html
python tools/measure/runner/light_page.py ancient-test.html ancient-measure.html
python tools/measure/runner/compare.py ancient-test.html measure-comparison --light=ancient-measure.html --matches=3,7,11 --ticks=1600 --par=2
node tools/measure/runner/profile.cjs ancient-test.html measure-comparison/legacy/case/_rec_3.js
node tools/measure/runner/profile.cjs ancient-test.html --control=3,1600
```

Реальный браузерный тест включается переменной `SIM_RUNNER_BROWSER_TEST=1`. `compare.py` создаёт новую папку, сохраняет все исходные записи и пишет `comparison.json` с выборками, пиками, временем, расхождениями и списком выживших процессов. Если исходы расходятся, команда возвращает ненулевой код. `profile.cjs` запускать отдельно от замера памяти и скорости, поскольку в нём есть дополнительные чтения и принудительный GC.

Поля существующего запроса GitHub Runner после освобождения ПК:

```json
{
  "par": 2,
  "shared_browser": true,
  "stream_records": true,
  "jobs": [
    {
      "label": "light_ancient",
      "ref": "<тот же SHA игры, что у базы>",
      "map": "ancient",
      "matches": [3, 7, 11],
      "light_page": true
    }
  ]
}
```

Для парного сравнения снять `shared_browser`, `stream_records` и `light_page` при той же постановке. Без этих полей остаётся штатная топология. В workflow прогоны запускает пуш в `measure/**` или ручной запуск. Пока ПК занят, проверка выполнялась короткими локальными сериями вне него.
