## Коротко для владельца (12 пунктов)

1. **Стек.** TypeScript в строгом режиме, постепенно, в том же проекте; симуляция — отдельно от показа (в браузере — в фоновом потоке
   Web Worker, для замеров — в Node без браузера, один и тот же код).
2. **Игровой движок** (Godot, Unity) — **не нужен.** Рисование занимает 0,5 мс за кадр; все длинные кадры — это расчёт хода игры, а не
   картинка. Движок не чинит ни одной причины повторных ошибок и уводит игру из браузера.
3. **В Rust — ничего сейчас.** Замерено: Rust в браузере (WASM) быстрее хорошего JS лишь в 1,2 раза на поиске пути и в 1,55 раза на
   лучах; нативно — 2,1 и 1,4. А те же расчёты на JS с плотными массивами вместо объектов — в 2,7 раза быстрее нынешних, и 51 % поисков
   пути повторяются. Rust остаётся опцией (этап R6) для двух ядер — поиск пути и лучи — только если после R4 замеры на вашем ПК покажут,
   что их не хватает. Условие: общий набор математики, иначе ломается «бит в бит» (замерено: 384 из 3000 путей расходятся из-за `hypot`).
4. **В TypeScript** — всё, где живут решения: знание о врагах, восприятие, задачи и арбитры, бой, гранаты (логика), движение, экономика,
   матч, тактики, карта и навигация. Типы ловят до запуска: «путь или прямая», единицы (пиксели / юниты CS2), тики или секунды, углы,
   «истина или знание бота», «задача поставлена — исполнена — отказано».
5. **Остаётся на JS** — показ: рисование 2D и 3D, табло, киллфид, обсервер, повтор клатча, редакторы карты, звук. На игру они не влияют.
6. **Ускорить без смены языка:** убрать повторные поиски пути и лучей (кэш на тик / на запрос), плотные массивы в поиске пути, быстрый
   поиск «в каком куске навмеша точка», первый тик раунда (пик до 1,9 с) — во фриз, рост памяти. Каждое — с проверкой «бит в бит».
7. **Новое ядро не нужно.** Перестройка 15–17.11 уже дала правильный скелет (модули, владельцы полей, запрет замков, арбитры, отдельный
   показ, детерминизм). Её надо **закончить**: закрыть чтение «истины» врага, дать арбитрам ответ «принято / отказано», хозяина каждому
   полю, полный снимок состояния.
8. **Оставляем** из нынешних решений: модули с номерами и сборку, `owners.json` и проверку сборки, арбитры `TASK_LEVEL`, `LOOK_LEVEL`,
   `fightState`, `moveSpeedTick`, `nadeTask`; набор карты `MAP`; запись матча и отпечаток «бит в бит»; отметки и снимки; сцены
   `rebuild/scenarios.json`; замеры на вашем ПК через GitHub.
9. **Почему ошибки будут повторяться реже:** каждый найденный класс ошибки закрыт механизмом, а не дисциплиной — тип (единицы, путь,
   знание), проверка сборки (кто пишет поле, кто читает «истину»), инвариант в каждом прогоне, сцена в реестре поведения, которая
   проверяется при любой правке рядом. Правка показывает, каких соседних механик она касается (анализ влияния по графу вызовов и полей).
10. **Порядок:** R0 опора для проверок (тесты, инварианты, база на ПК) → R1 TypeScript в сборке → R2 контракты устройства по каналам
    (место → гранаты → ход → взгляд → бой → знание → команда) → R3 симуляция в Worker и Node → R4 скорость → R5 исправления поведения по
    реестру → R6 Rust — только по замеру. R0–R4 игру не меняют (проверка «бит в бит»).
11. **Риски:** отдельный шаг может не перенестись «бит в бит» — тогда он делится или проверяется 8/16 матчами; типы не ловят «что лучше
    сделать» — это остаётся сценам и вашему глазу; часть исправлений ждёт ваших ответов (фетч укрытия, какой путь «нового матча»
    правильный); скорость на вашем ПК этим этапом не мерилась — цели по мс ставятся после базы R0; объём — оценка (~20–30 сессий R0–R5).
12. **Возврат к развитию игры** — после R0–R2 (≈ 9–15 сессий): тогда правки поведения идут уже по новым правилам (сцена → хозяин →
    проверки). R3–R4 можно вести параллельно с развитием. Перестройка закончена, когда выполнены 12 измеримых критериев
    (`MIGRATION_ROADMAP.md` §4).
