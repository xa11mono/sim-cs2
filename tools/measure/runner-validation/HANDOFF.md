## Что проверено по семи пунктам

|---|---|

Для общего Job Object проверен сценарий увеличения лимита после того, как внешняя нагрузка освободила память во время активной фазы. |
| 2. Прогноз на пару движок / карта | В `v637a` наблюдённые пики разделены по парам, но начальная оценка игнорирует настройку `est_mb["движок:карта"]`. Исправлено. Валидные восстановленные пики заранее заполняют историю, а пара без законченного измерения начинает с одного калибровочного матча. При последующем росте оценка обновляется. |
| 3. Общий всплеск памяти | Допуск `v637a` при 8293 МБ свободных и запасе 3195 МБ пропустил бы 5 холодных Chromium Ancient с прогнозом 1000 МБ. При одновременном достижении наблюдённого в 332 пика 2153 МБ им потребовалось бы 10 765 МБ. Добавлены общий и отдельный Windows Job Object. Node и браузер запускаются после подтверждения обоих назначений. Холодный запуск ждёт доступного бюджета, даже если в пуле ещё нет матчей. |
| 4. Повторы и последующие фазы | Исходный тест `v637a` уже подтверждает, что повторы идут по одному и не переносят `cap=1` в следующую фазу. Сохранено. Новый тест проверяет восстановление, повторы и полный `par=8` в следующей фазе на общей модели. |
| 5. Resume 332 | Из реальных файлов принято **25 из 34** отпечатков при версиях среды 332. В очередь попали ровно **9** матчей. Отменённый Chromium Mirage №29 имеет пустой отпечаток и статус остановки. Новая процедура проверяет коммит, карту, движок, номер, хэши инструментов, версии рантайма, полный формат отпечатка и успешное завершение. Атомарный маркер записи кеша ставится последним. |
| 6. Фактическая параллельность и производительность | Старый отчёт включал устаревшие `guard_*`, считал попытку с ошибкой за сыгранный матч и терял первую попытку, если файл перезаписал повтор. Новый отчёт берёт попытки текущей фазы из пула. Отдельно показывает принятые из архива отпечатки, успехи, ошибки, незапущенные матчи и повторы. |
| 7. Повторные сборки и вычисления | В 332 было 4 реальные сборки, 8 запросов `git fetch` и 6 повторных проб среды. Новый код закрепляет ref один раз, кеширует сборки по коммиту, карте и варианту, проверяет среду один раз на движок. Resume с архивом 332 планирует 2 сборки Mirage и 9 матчей. Все четыре полностью восстановленные фазы обходятся без сборки и запуска матчей. |

## Как читать новый отчёт

Один `phase.json` на метку. Начало и завершение попыток фиксируются монотонными часами. Завершение отмечает ожидание процесса в отдельном потоке, поэтому время не округляется до шага опроса. `par_max` — максимум пересечений интервалов. `par_avg` — сумма времени работы всех попыток, включая неудачные, делённая на время фазы. `ticks_per_s` и `matches_per_hour` используют только результаты успешно завершившихся свежих расчётов и общее время фазы. Это производительность раннера, включая запуск процессов и повторы. Скорость отдельной функции ядра замеряется отдельно.

`complete_fresh_sample` означает, что все результаты получены в этой фазе. `complete_without_retries` дополнительно требует, чтобы каждый матч прошёл с первой попытки. Для сравнения движков сопоставляются одинаковые карты, номера матчей, версии среды и фактическая параллельность. Отчёт продолжения 332 даёт скорость только свежего остатка задания. Старые значения времени туда не попадают.

## Воспроизведение

Из корня репозитория. Команды читают Git и запускают локальные тесты.

```sh
git fetch --no-tags origin v637a pc-results/332 measure/v636a-r5core
python3 tools/measure/runner-validation/inspect_332.py
python3 tools/measure/runner-validation/test_runner.py --archive -v
python3 tools/measure/procguard_test.py
```

Короткая проверка реальных процессов использует имеющиеся сборки Mirage с коммита игры 332. Нужны Node и установленный Playwright с Chromium. Она не является эталоном скорости.

```sh
python3 tools/measure/runner-validation/smoke_short.py dist/core-mirage.js dist/mirage.html
```

В облаке прошли 12 из 12 применимых сценариев независимого набора. Один сценарий с настоящими Windows Job Objects пропущен. Исходный набор сторожа прошёл до и после исправлений. Короткие Node и Chromium сыграли по 1200 тиков Mirage и выдали одинаковый отпечаток. Факты архива и короткого прогона записаны в `evidence-332.json` и `evidence-short.json`.

## Передача Claude

`request-332-resume.json` — заготовка функционального продолжения. В ней закреплены оба исходных Git-коммита. Она лежит рядом с тестами и сама не запускает Actions. Для принятия архива нужен Windows x64 с совпадающими Node/V8, а для Chromium — также совпадающими Playwright, версией браузера, UA и V8 Chromium. При изменении среды конкретный результат не восстанавливается. Совместимость локального кеша проверяется той же идентичностью запроса и среды. В отчёте проверка импорта воспроизведена на опубликованных файлах с подставленной зафиксированной версией Windows-среды. Доступ к кешу на ПК для этого не требовался.

Общий Job Object ограничивает суммарный **commit** процессов матчей, а запас физической памяти учитывается при допуске и опросе. Рабочие наборы, общие страницы и внешние приложения влияют на физическую память отдельно. При отказе назначения Windows-защиты запуск останавливается. Нативный тест Job Object предусмотрен в наборе, но фактическое вложение Job Objects под Windows и скорость при полной параллельной нагрузке в облаке не подтверждены.

## Допуск Chromium и Node по текущей памяти

Chromium и Node используют текущие размеры деревьев своей пары и свободную RAM. Резерв новых деревьев до первого замера берётся из
существующей настройки `est_mb` и наблюдений по паре. Firefox и WebKit сохраняют калибровку по одному матчу и резерв роста до пиков.
В смешанной очереди прогноз роста строгих движков сохраняется. Пределы памяти машины и деревьев также используются в динамическом режиме.

На Windows при допуске Chromium и Node сравнивается текущий commit общего Job Object и бюджет следующего старта.
При недоступном замере используется прежняя сумма прогнозных пиков. Запись недопуска показывает, чего не хватило: RAM или commit.
После ненулевого выхода в конкурентном Windows Job Object разрешён один изолированный повтор Chromium или Node.
Первый выход остаётся в списке попыток, повтор завершает матч только после проверки результата. Причина выхода при этом не предполагается.

Воспроизведение `python tools/measure/runner-validation/test_runner.py -v`. Снимок из уведомлений Actions прогона 334:
15 977 МиБ всего, 6 008 МиБ свободно, два дерева Chromium Ancient 1 972 и 1 018 МиБ, предшествующий пик 2 208 МиБ.
Старый арифметический допуск оставляет 2 374 МиБ при требуемом запасе 3 195 МиБ. Новый допускает ещё одно дерево.
Отдельная модель проверяет ограничение общим Job Object при свободной RAM, рост лимита после освобождения памяти,
резкое одновременное увеличение commit и изолированный повтор. Реальный Windows Job Object и производительность полного прогона
на ПК требуют отдельной проверки на Windows.
