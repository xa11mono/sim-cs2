## A. Сохранение существующих автономных HTML-сборок

**Что есть:** `ancient-radar.html` 15,83 МБ, `mirage-radar.html` 9,43 МБ; открываются как файл, работают офлайн,
вся игра внутри. Измерено: готовность 0,57–1,01 с, память страницы 80–137 МБ, 200 FPS.

**Плюсы:** ничего не ломается; один файл можно отправить/положить на страницу; отметки и правки владельца уже
работают; нет зависимости от сервера.

**Минусы:** 4,35 МБ общего (движок, звуки, шрифты, CSS) дублируются в каждой карте; при 7 картах — 30 МБ копий;
правка движка требует пересборки всех страниц; вес файла мешает AI-агентам и Graphify; невозможно отдать
«движок один раз».

**Вердикт:** **сохранить как дополнительный формат** (офлайн-артефакт, «одна страница — вся игра»), но не как
единственный. Это ценно владельцу и не мешает остальным вариантам.

## B. Отдельные HTML-страницы с общим движком и внешними ресурсами

**Что:** `index.html` + `engine.js` (2,0 МБ) + `maps/<id>.map` (пакет данных) + `sounds.*` + `fonts.*` + `hud-photos.*`.
Каждая карта — отдельная страница/URL, движок общий и кэшируется.

**Измерено, что даёт:** снятие base64 с геометрии — −2,45 МБ Ancient / −0,52 МБ Mirage и ≈ −270 / −90 мс CPU на
декодирование; перенос звуков (1,71 МБ) и фото (0,43 МБ) за первый кадр не влияет на симуляцию. Повторная загрузка
при `immutable`-кэше — почти 0 байт (гипотеза по механике HTTP-кэша, не измерялась в этом аудите).

**Плюсы:** одна копия движка; каждая карта — независимый пакет; кэш; проще добавлять карты; AI-агенты видят
исходники и данные, а не 16 МБ HTML. Отметки не меняются: ключ хранилища уже per-map (`MAP.store`).

**Минусы:** нужен локальный сервер (или `file://` с ограничениями `fetch`); загрузка становится асинхронной —
`MAP` сейчас нужен синхронно на верхнем уровне (`var MAP` в 010, `applyWalls` 030, `computeZoneDanger` 060), значит
нужен `boot(map)` и аккуратный перенос инициализации, иначе игра начнёт стартовать иначе; две точки правды
(движок/пакеты) требуют версионирования.

**Вердикт:** **основной ближайший шаг**, если владелец согласен на страницу с сервером/внешними файлами.

## C. Единая точка входа с динамическим выбором карты

**Что:** один `index.html`; список карт в `maps/index.json`; выбор карты на экране; данные подгружаются, движок
один; при смене карты — пересоздание состояния (`MAP` → пересборка навмеша/видимости) без перезагрузки страницы,
если получится, иначе перезагрузка с `#map=ancient`.

**Плюсы:** один URL для владельца и CS2 Manager; удобно сравнивать карты; одна вкладка — один движок.

**Минусы:** смена карты в одном процессе = повторная инициализация навмеша/видимости (0,4–0,7 с, измерено для
загрузки) и память двух карт при переключении; риск утечек (сейчас в памяти 137 МБ Ancient); `freshMatch`
и снимок отметок привязаны к глобальному состоянию.

**Вердикт:** делать **после B**, как надстройку: выбор карты + перезагрузка состояния. Не начинать с C.

## D. Локальное приложение с TypeScript-интерфейсом и Rust Native

**Что:** окно (Electron/Tauri/свой UI), логика на TS, тяжёлое — Rust: лучи (`m3Cast`), гранаты (`nadeLaunch/Step`),
навмеш. Рендер 2D/3D — на чём-то нативном (wgpu/OpenGL) или оставить web-слой.

**Измерено в `bench/stage3`:** Rust Native на тех же данных: `sight` 1,567 мс против 2,926 мс JS (1200 лучей),
`throwFlight` 1,169 против 2,077 мс (48 бросков), `nav` 22,4 против 33,2 мс JS-opt (400 маршрутов);
RSS ядра 84 МБ; загрузка данных 83 мс. Точность: 1200/1200 лучей, 900/900 ходов, 48/48 бросков совпали
(у Mirage 1195/1200 лучей — известное расхождение Triple Box).

**Плюсы:** самый быстрый старт и лучшая память; нет браузера; удобно для CS2 Manager (локальный процесс, файлы,
сокеты); можно гонять матчи пачками.

**Минусы:** надо написать весь UI/рендер заново (сейчас 1,0 МБ исходника HUD + 62 КБ draw + 119 КБ 3D);
отметки/снимки/перемотка — заново; перенос логики TS — это переписывание 1300 функций; владелец теряет привычную
страницу.

**Вердикт:** **не первый шаг.** Реалистично — после фаз 1–3 (каналы) и только для «движка матчей», с web-UI сверху.

## E. Браузерная версия с TypeScript и Rust WASM

**Что:** та же страница, логика на TS (сборка esbuild/tsc), тяжёлые ядра — Rust → WASM (91,7 КБ wasm, как в
`bench/stage3`), вызовы через границу.

**Измерено:** WASM: `sight` 1,802 мс, `nav` 24,3 мс, `throwFlight` 1,84 мс — быстрее JS, но медленнее нативного
Rust; инстанциация 0,43 мс, копирование входа 10 мс; память WASM 188 МБ (бенчмарк с полным набором данных);
граница JS↔WASM на одиночный луч — дорогая (в бенчмарке пакет 1000 вызовов — 1,14 мс, одиночный вызов ~1,1 мкс).

**Плюсы:** сохраняет браузер и распространение (B/C), ускоряет горячие точки; один код ядра с D (общий Rust).

**Минусы:** память (188 МБ на данные + браузер), сложность сборки (Rust + wasm-bindgen/ручной ABI), отладка;
выигрыш в общем FPS нулевой на этой машине (2D/3D уже 200 FPS), выигрыш только в старте/массовых прогонах.

**Вердикт:** **точечно**: сначала измерить, что именно болит (старт 0,67 с на навмеш/видимость — вот кандидат),
и вынести в WASM только это, не всю игру.

## F. Общая архитектура с поддержкой нативного и браузерного запуска

**Что:** одно ядро (TS-логика + Rust-вычисления) с двумя хостами: браузер (WebGL/Canvas UI, WASM) и нативное
приложение (свой рендер). Общие данные карт (бинарные пакеты), общий протокол состояния, разные оболочки.

**Плюсы:** один источник правды; можно гонять массовые матчи нативно и смотреть в браузере; CS2 Manager
интегрируется и так, и так; AI-агентам — один набор исходников.

**Минусы:** самая большая работа; два UI; риск «двух игр» (разошлись рендер/ввод); отметки и снимки надо
поддержать в обоих; тесты должны сверять ядро (как в stage3: каждый луч/бросок).

**Вердикт:** **целевая картина на потом**, после того как каналы (фаза 3) разделены и ядро проверено на бит в бит.

## Рекомендуемый порядок (без миграции до согласования)

1. **Сейчас — B как формат распространения** (движок отдельно, карты пакетами, звуки/фото/шрифты внешними
   файлами), **A сохранить** как офлайн-артефакт. Игра не меняется: это упаковка, а не логика. Проверка —
   отпечаток и сверка лучей/бросков.
2. **C** — после B, как один URL с выбором карты (с перезагрузкой состояния при смене).
3. **TypeScript** — по мере переноса каналов (фаза 3): каждый канал уже модуль, типы состояния — из
   `rebuild/gen/vars.json`; бит в бит после каждого шага.
4. **Rust/WASM** — после TS-границ: сначала только лучи/гранаты/навмеш (там измерен выигрыш), с проверкой
   «каждый луч и бросок совпал» (методика stage3).
5. **D/F** — только когда ядро отделено и есть смысл во втором хосте; не раньше.

Ни один пункт не начинать без утверждения архитектуры владельцем (прямое требование задания).
