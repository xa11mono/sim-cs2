## 2. Подробно о главных расхождениях

### 2.1. Точность навмеша (№7)

DeepSeek в одном документе требует «не менять точность: … навмеш … бит в бит» (RESOURCE §10) и в нём же предлагает «≈ 4 байта ×
координата» и `Int16/Float32` (RESOURCE §3, §8; REC §2.2). Проверка всех чисел `navmesh.json` показывает: каждое второе число в 32 бита не
помещается (`evidence/navmesh_precision.txt`). Это изменило бы граф пути, а значит маршруты и матчи.

**Как правильно:** переупаковка данных карты — только без потерь (Float64, либо целые там, где все значения целые, — это проверяется
скриптом по каждому полю); приёмка — равенство разобранных значений поле за полем (хэш по битам каждого числа), а не размер и не суммы.

### 2.2. Цена границы WASM (№10)

Пустой вызов WASM из JS: Node 22 — 2,9 / 6,9 нс (два замера), Chromium 158 — 2,7 нс (главный поток) и 2,8 нс (Worker), JS-функция — 0,5–3,7 нс.
N-API (нативный Rust из Node): 20,8 нс на вызов с числом, ~112 нс с массивом из 8 чисел (`evidence/call_cost.json`). Для поиска пути
(~300 мкс на запрос, этап 3) граница — сотые доли процента; для одного луча (~1,5 мкс) — от 0,2 % (WASM) до 1,4–7 % (N-API). Вывод: дорогая
не граница, а **передача изменяемого состояния** (граф с отключёнными рёбрами, дым, огонь, знание бота — `knownSegCost`) и поддержка
двух реализаций. Лучи — пакетом на тик, путь — одиночными запросами.

### 2.3. Окно замера кадров (№14)

У DeepSeek 0 длинных задач за 8 с, у этапа 3 — 6 кадров > 50 мс за 1090 кадров. Противоречия в данных нет: пики — первые тики раунда
(К-6 этапа 3), окно DeepSeek их не включает. Порог 50 мс — определение длинной задачи браузера (Long Tasks API), не выдуман.

### 2.4. Зависимость игры от движка JS (№17, пробел)

Не рассматривался ни DeepSeek, ни этапом 3 («Node-прогон = браузерный» — критерий 12 этапа 3 предполагал это равенство). Проверено:

| пара | различаются (из 200 000 входов; atan2 — из 200 000 пар) |
|---|---|
| Chromium 158 ↔ Node 22 (оба V8) | sin, cos, tan, atan2, exp, log, pow (из 20 000: 704 / 681 / 728 / 3440 / 1985 / 243 / 2035); hypot и sqrt — равны |
| Node 22 ↔ Rust `libm` (нативно и WASM) | sin 1831, cos 1893, log 212, pow 8861, hypot 72 958; tan, atan2, exp, sqrt — равны; разница ≤ 1 ulp (hypot ≤ 2) |
| Rust std нативно ↔ Rust std WASM | sin, cos, tan, atan2, exp, log, pow, hypot — различаются (std берёт математику платформы) |
| Rust `libm` нативно ↔ Rust `libm` WASM | **0 различий** во всех функциях |
| sqrt — везде | **0 различий** (IEEE, правильно округлён) |

Chromium 158 даёт правильно округлённые sin / cos / tan / atan2 / exp / log (5000 из 5000 против эталона mpmath, 200 бит), Node 22 — нет
(4132–4932 из 5000) (`evidence/math_correct_rounding.txt`). Значит, V8 сменил реализацию между этими версиями. Проект об этом знает
частично: на ПК закреплён Playwright 1.56 с комментарием «другая версия браузера — другой движок JS, матчи расходятся»
(`tools/measure/remote_run.py:23`), но в облаке сейчас Playwright 1.63 / Chromium 158, а не та версия, о которой говорит комментарий.

На игре: тот же матч в Chromium 158 с `Math.sin/cos/atan2/exp/log/pow`, заменёнными на `libm` (разница ≤ 1 ulp), расходится по хэшу
позиций **на первом контрольном отрезке (16 тиков)**, к тику 20 000 — разный номер раунда (4 против 3); без замены два прогона совпадают
бит в бит (`evidence/game_math_sensitivity.json`).

**Следствия:** (а) отпечаток «бит в бит» сравним только в одной версии движка JS; (б) Node-прогон для массовой симуляции не совпадёт с
браузером; (в) снимок отметки владельца (его Chrome) может не воспроизводиться в Playwright другой версии; (г) Rust-ядро не может совпасть
с JS, пока JS зовёт `Math.*` движка. Решение — `ARCHITECTURE_ADDENDUM.md` §2.

- Вариант B (общий движок + пакеты карт) и сохранение автономного HTML (A) — **да**, с поправками №7, №21.
- `map3d` без base64 — **да** (без потерь).

- Удаление мусора (`mirage-radar-check.html`, `.tmp/probe`, `__pycache__`, генерируемые `bundle.bin`) — **да**, после проверки, что их
  никто не читает (DeepSeek это проверил по ссылкам; повторить `grep` перед удалением).
- Порядок «B → C», «D/F — после разделения ядра» — **да**, но D без переписывания показа (№13).
- Единые команды — **да**, одной точкой входа на Node (№19).
