## 1. Распределение по языкам

| что | язык | почему |
|---|---|---|
| решения ботов, знание, задачи, арбитры, бой, гранаты-логика, экономика, матч, тактики, загрузка пакета | **TypeScript** | здесь классы ошибок смысла (этап 3, REGRESSION_PROTECTION); ловушки переноса на Rust (ниже) — именно в этом коде |
| поиск пути (`zoneDijkstra` + `knownSegCost`), лучи (`m3Cast`, `m3SegTri`), полёт гранаты (`nadeLaunch` / `nadeStep`), таблица прострелов при загрузке (`computeZoneDanger`), сборка графа при загрузке (`rebuildNav`) | **Rust**: нативно (Node / Electron) и WASM (браузер) — одна библиотека `kernels/` | чистые вычисления над массивами; выигрыш измерен (этап 3: нативно 1,4–2,1×, WASM 1,2–1,55× поверх JS на массивах; DeepSeek: нативно 1,5–1,9×) |
| общая математика `dmath` | **TS и Rust**, один алгоритм | §2 |
| показ, HUD, обсервер, редакторы, повтор клатча, звук | **JS как есть** (по желанию — TS позже) | не влияет на игру; требование сохранить вид |

**Rust-ядро принимается**, только если выполнены оба условия (числа порогов не назначаются заранее — сравнение с шумом измерения):
1. *Корректность*: каждый ответ ядра равен ответу эталона на TypeScript бит в бит — на записанном корпусе реальных запросов из матчей
   (все карты) и на отпечатке матчей во всех средах запуска (браузер, Node, нативно). Сумма или доля совпадений — не доказательство
   (`DEEPSEEK_REVIEW.md` №8, №9).
2. *Польза*: в целевом сценарии (массовая симуляция на ПК владельца, старт страницы) время улучшилось больше, чем разброс повторных
   замеров того же сценария; цена интеграции (передача состояния, копирование) входит в замер.

TS-эталон каждого ядра остаётся: он — проверка, запасной путь и место, где агенты читают логику.

**Почему логика не переносится в Rust** (подсчёт по коду расчёта, `evidence/porting_ops.txt`): `Math.round` 256 мест (в JS −2,5 → −2,
в Rust −3), `Math.min/max` 527 (в JS NaN заражает, в Rust — отбрасывается), `.sort(` 98, `for…in` 105 и `Object.keys` 57 (порядок
ключей JS). Каждое — тихое расхождение при переносе. В ядрах их единицы, и они закрываются тестом на корпусе.

## 2. Детерминированная математика — новое обязательное условие

**Факт** (`DEEPSEEK_REVIEW.md` §2.4): `Math.sin/cos/tan/atan2/exp/log/pow` дают разные биты в Chromium 158 и Node 22; Rust std — разные
нативно и в WASM; игра расходится с первых тиков при разнице в 1 ulp. Сейчас в коде расчёта: sin 61, cos 64, atan2 108, atan 6, acos 1,
exp 14, log 11, pow 8, hypot 968 вызовов. `sqrt` и `+ − × ÷` совпадают везде (IEEE).

**Решение:** модуль `dmath` — свои sin, cos, atan2, atan, acos, exp, log, pow, hypot из одного алгоритма в TS и в Rust, только на `+ − × ÷ √`
и операциях с битами, без FMA, без вызовов математики движка. Кандидат — перенос `libm` (Rust-порт musl): измерено, что `libm` даёт
одинаковые биты нативно и в WASM (0 различий из 200 000 по всем функциям). TS-перенос проверяется на равенство с Rust `libm` на том же
корпусе. Вызовы `Math.sin` и др. в коде расчёта заменяются на `dmath` через правило сборки (запрет `Math.<трансцендентная>` в `engine/`).

**Это изменит биты игры** — один раз и по объяснимой причине. Поэтому это отдельный шаг «нормализация математики» (`ROADMAP_CHANGES.md`,
Р1) со своей приёмкой: первый расходящийся тик найден, расходящийся вызов назван, разница вызова ≤ разнице реализаций (единицы ulp),
дальше — новая база. Статистика матчей — только как дополнительная проверка, что ничего не сломано.

**До этого шага:** каждый отпечаток и каждая отметка записывают среду (браузер, версия, V8 / Node); сравниваются только записи одной среды.

**Не измерено:** скорость `dmath` в JS против встроенных `Math.*` — прототип в Р0; `hypot` (968 вызовов) можно сразу считать как
`sqrt(dx²+dy²)` — `sqrt` совпадает везде (но биты изменятся — входит в тот же шаг нормализации).

## 5. Автономные HTML-сборки

**Проверено** (`bench/make_standalone.js`, `br.js`, `evidence/math_chromium_standalone.json`): один HTML по `file://` в Chromium 158 —
WASM в base64 внутри файла, расчёт в главном потоке и в Worker, созданном из Blob, с WASM внутри Worker — работает; результаты `libm`
в странице и в Worker равны нативным бит в бит. WASM-ядро — 55 КБ (прототип), 92 КБ (бенчмарк DeepSeek): на фоне 9–16 МБ страницы
незаметно.

**Не проверено:** страница-артефакт claude.ai (разрешены ли Worker из Blob и компиляция WASM); Chrome владельца. Это проверка Р0 на
закрытой тестовой странице — только с разрешения владельца. Запасной путь, если запрещено: симуляция в главном потоке (как сейчас), тот же код.

Сборка выдаёт из одних артефактов: (а) автономный HTML одной карты (как сейчас); (б) автономный HTML со всеми картами (движок один раз +
пакеты); (в) вариант B (движок + пакеты файлами). Внешне страница не меняется — проверка снимками экрана (`tools/page/broadcast_shot.js`)
до / после, не только отпечатком.

## 6. Общий движок и пакеты карт

Принимается вариант B DeepSeek с поправками:
- **Без потерь**: числа пакета — Float64 или текст; `Int16/Float32` для навмеша опровергнуты (`DEEPSEEK_REVIEW.md` №7). Целые типы —
  только для полей, где скрипт проверил, что все значения целые и в диапазоне (так уже сделано в `map3d`: `Int16Array` для вершин).
- **Приёмка пакета**: хэш битов каждого разобранного числа по каждому полю `MAP` до / после равен; затем отпечаток матчей.
- **Схема пакета** — типы TS из `tools/map/map_manifest.json`; загрузчик проверяет схему и версию.
- **Независимость карт**: названий карт в коде нет (проверено, `DEEPSEEK_REVIEW.md` №4), но остались допущения из `docs/ARCHITECTURE.md`
  («Что код всё ещё считает общим»): радиусы в пикселях под `pxUnits` = 2,5, веса сетапов CT по id Ancient, два сайта, пространство
  2048×2048. Их перенос в пакет или в перевод единиц (`GameUnits`, этап 3) не меняет игру на нынешних картах, если значения совпадают —
  проверяется бит в бит.
- **`boot(map)`**: явный порядок инициализации (`applyWalls` → `rebuildNav` → `computeZoneDanger`) — после того, как этот код стал модулями
  (этап 3 R2), иначе меняется порядок загрузки.
- **Тяжёлая инициализация** (навмеш + прострелы 0,47–0,67 с, DeepSeek LOADING §3) — кандидат Rust-ядра или кэша в пакете (запечь таблицу
  прострелов при сборке пакета; равенство с расчётом при загрузке — бит в бит).

## 7. Структура папок без числовых префиксов

```
engine/          симуляция, TypeScript, без DOM и без показа
  core/          тик, настройки, математика dmath, типы, реестр состояния (снимок)
  map/  nav/  sense/  know/  team/  bot/  nades/  match/  debug/
kernels/         Rust: route, ray, flight, dmath — одна библиотека → нативно (N-API) и WASM
view/            показ (JS как есть): draw, 3D, hud/, observer, replay, sandbox, editors/, page/
maps/<карта>/    исходники карты и пакет (сейчас data/maps)
tools/           build, check, measure, marks, map, debug — одна точка входа на Node
docs/            действующие документы; архив — docs/archive
dist/            артефакты сборки (не в git)
```

Полная карта 90 файлов → новые имена — `STRUCTURE_MAP.md` (проверена скриптом: все файлы учтены, имена не повторяются). Правила:
- имя — что делает механика (`bot/look.ts`, `nades/flight.ts`); не больше одного уровня группировки внутри `engine/`;
- порядок загрузки — из импортов; пока файл не модуль, порядок держит **один список** `engine/order.json`, а не имена;
- переименование — отдельный шаг, **бит в бит**, после того как порядок явный; в том же шаге обновляются `rebuild/*.json`, таблица «Где что»
  в `CLAUDE.md`, `docs/ARCHITECTURE.md`. Цена: имена с номерами встречаются в ~80 файлах вне архива (`docs` 25, `tools` 24, `src` 18,
  `rebuild` 11, корень 4); ссылки вида «(110)» и «350:381» в комментариях кода — сверх этого, их переводит тот же скрипт по карте имён.

можно ли ему верить. Старые снимки читаются переходником, пока нужны.

## 9. Причинно-следственный дебаг

Требование — фактические рассмотренные действия, причины выбора, результат арбитража, исполнение. Сейчас есть части: причины у хозяев
(`_walkWhy`, `_runWhy`, `lookReason`, `_task.tag`), текстовый журнал `dlog` (`645_decision_log.js`: смена задачи, гранаты, взгляд — 15 с,
лежит в боте и в снимке), разбор команды (`612_team_debug.js`).

**След решения** — одна запись на решение хозяина (позиция, взгляд, ход, режим боя, граната, команда):

| поле | что |
|---|---|
| `tick`, `bot`, `channel` | когда, кто, какое решение |
| `know` | на что опирался: записи знания (источник, время, точность) |
| `options[]` | рассмотренные варианты с факторами оценки (не только победитель) |
| `dropped[]` | отсеянные — чем (запрет и его причина) |
| `chosen`, `why` | выбор и причина |
| `claim` → `arbiter` | заявка, ответ арбитра: принято / отказано, кем, уровень |
| `exec` | исполнено ли, на каком тике; кто перезаписал и почему |

Правила: запись делает только хозяин (у него есть варианты); след лежит **вне состояния игры** (кольцевой буфер наблюдателя, не в боте);
выключен — ноль работы; включён — игра бит в бит та же (тест «след вкл / выкл»); `dlog` становится видом этого следа. Запрос:
`node tools/sim.js why <отметка|снимок> <бот> <тик>` печатает цепочку из правила CLAUDE.md §5 («что бот знал → варианты → отсеяно →
выбрано → записано → исполнено → перезаписано → пересмотр»).

  `KnowledgeView` / интерфейсы), какие варианты и причины кладёт в след, сцены A/B. Сборка проверяет карточку против кода (как
  `owners.json` сейчас).
- **Новое поведение = строка у хозяина**: вариант с весом в его оценке, а не новая функция рядом (правило CLAUDE.md §7 сохраняется).
- **Анализ влияния** (этап 3) печатает задетые механики и сцены для изменённого файла.
- **Шаблон**: команда `node tools/sim.js new-mechanic <имя>` создаёт файл с карточкой, сцену и строку реестра — агент не придумывает
  устройство заново.

## 11. Общие инструкции агентов, Graphify, Ponytail

- **Одни инструкции**: `AGENTS.md` — единый источник правил (его читает Codex); `CLAUDE.md` подключает его строкой `@AGENTS.md` и добавляет
  только то, что относится к Claude Code; для агентов без доступа к репозиторию (ChatGPT, DeepSeek в чате) команда
  `node tools/sim.js context <тема>` собирает текстовый пакет: `AGENTS.md` + карточки нужных механик + карты устройства + пакет отметки.
- **Graphify** ([Graphify-Labs/graphify](https://github.com/Graphify-Labs/graphify)): граф знаний по папке (`graphify-out/`: `graph.html`,
  `GRAPH_REPORT.md`); код разбирается локально, тексты документов уходят в API модели. Место в проекте — **навигация**, не правда о
  связях: правду дают `rebuild/gen` (разбор кода при сборке, проверяется). Запуск — по `engine/`, `view/`, `tools/`, `docs/`, без `dist/`,
  `maps/*` и архива; `graphify-out/` — не в git (или только `GRAPH_REPORT.md`). Его хук, перехватывающий поиск, — по решению владельца.
- **Ponytail** ([dietrichgebert/ponytail](https://github.com/dietrichgebert/ponytail), [обзор](https://betterstack.com/community/guides/ai/ponytail-ai/)):
  «лестница решения» — нужен ли код вообще → есть ли в проекте → в стандартной библиотеке → в платформе → в зависимости → одна строка →
  только потом новый код. **Адаптация для sim-cs2:** (1) может, это данные карты или пакета, а не код? (2) есть ли хозяин решения — строка у
  него; (3) есть ли общий помощник (`dmath`, `nearP`, `taskProp`, `KnowledgeView`); (4) только потом новое — и старое удаляется в той же
  правке. Ограничение: «меньше кода» ≠ «правка в месте симптома» — механика чинится во всех местах сразу (CLAUDE.md §5); безопасность,
  проверки на границах и наблюдаемость (след решения) не урезаются.

## 12. Наблюдение, эквивалентность и массовая симуляция

- **Наблюдатели без подмены функций.** Сейчас `fingerprint.js` и `rec2.js` оборачивают функции игры (`feedKill`, `throwNade`, `endRound`).
  С модулями и TS это перестаёт работать. Нужен интерфейс событий симуляции (подписка только на чтение) — он же для следа (§9),
  записи матча и Н1.
- **Локатор расхождения** (новый инструмент Р0): хэш **полного** реестра состояния каждый тик (сейчас отпечаток берёт только x, y, взгляд,
  HP, оружие, деньги — внутреннее расхождение знания или задачи видно с опозданием), первый расходящийся тик → поле → запись вызовов
  ядра на этом тике → операция. Это делает «необъяснённое расхождение» объяснимым.
- **Правило эквивалентности** при чистом переносе (переименование, модули, TS, пакеты, Worker, Rust-ядро): бит в бит в одной среде; иначе —
  локализация до операции. Статистика матчей (8 / 16) — только для шагов, которые **намеренно** меняют игру (нормализация математики, позже —
  поведение).
- **Массовая симуляция**: Н1 (Node + `worker_threads`), после `dmath` матчи одинаковы на любой машине; куча ~72 МБ на матч после 30 000
  тиков (этап 3, `memory_mir.json`) — число параллельных матчей задаётся памятью ПК, замер на ПК — в Р0. Время в логике игры не
  используется (`performance.now` — только замер `NADE_SOLVE_MS`), `Math.random` в коде расчёта нет — препятствий для повтора нет.
