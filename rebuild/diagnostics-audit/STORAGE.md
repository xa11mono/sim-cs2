## Что удалось восстановить

Из GitHub прочитаны уже сохранённые `rec_3.json.gz` для четырёх условий прогона 320. [RECORD_EVIDENCE.json](RECORD_EVIDENCE.json) фиксирует ref, SHA, пути, числитель, количество строк и недостающие строки по каждому списку.

- **Ancient после dmath, матч 3:** `stall=118`, сохранено 40, **78 строк нет**. Все 40 сохранённых — ветка отказа задач, 39 в раунде 3, один в раунде 2. Встречаются `save → отказ lineup` и `endhunt → отказ anchor`. Вывод журнала Р2 о влиянии матча 3 обоснован числителем. По сохранённым строкам нельзя распространить объяснение 39 эпизодов на все 118 или назвать весь сдвиг физическим застреванием.
- **Mirage, матч 3:** до и после `nav=44`, в каждом файле 40 строк, **по 4 причины отсутствуют**. «Количество совпало» не означает совпадение состава причин. Для того же матча до dmath есть 30 начатых и 29 завершённых раундов. Агрегатор считает 30.
- **Двойной подсчёт:** проба P05 фиксирует две записи `stall` у одного непрерывного стояния; I25 — две записи для одного присваивания `heardSound`. Это подтверждённые контрпримеры к трактовке «число отдельных происшествий», а не оценка их распространённости.
- Исторический разбор допускает повтор на точной сборке и снимке с теми же входами (build hash, карта, настройки, память). Новый полный повтор создаёт новое доказательство. Он не восстанавливает исходные несохранённые строки, если историческая сборка, кадр, ключи или входы недоступны.

## Предлагаемый формат

1. **Одна атомарная запись на каждый вклад.** Внешний recorder получает типизированный event: `session_id, match_id, round_id, tick, phase, seq, metric_schema_version, metric_id, outcome, delta, episode_id, actor_id, target_id, reason_code, source_event_id, observed_facts_ref`. Поля по необходимости: `claim_id/throw_id/route_id`, прежнее/новое состояние, P3 и floor, место возникновения, код исключения и идентификаторы доказательства. `seq` однозначно упорядочивает события в пределах тика; точный текст генерируется из кода причины вне тика. Наблюдения о скрытом противнике хранятся в отдельном домене «истина для постфактум», без доступа из решений.
2. **Инциденты и знаменатели.** Все инкременты ссылаются на episode ID. Пример: один поток «заявка→ответ→исполнение→перезапись» под claim ID, один запуск и его эффекты под throw ID. Непрерывные повторные bot-tick-срабатывания группировать в запись span с началом, концом, количеством и однозначным правилом восстановления тиков; случаи с другими причиной/входами/пропусками идут отдельно. Один эпизод может иметь несколько тегов, но объединённый счётчик использует уникальные ID той единицы, которую обещает измерять. Отдельный ledger eligible/excluded/censored даёт знаменатель и причинное исключение. Закрытие раунда, смерти или отсутствия поля не приравнивать к нулю.
3. **На тике минимальная работа, полные данные на диск.** Фиксировать в существующем событии у хозяина компактный числовой payload в пределах горячего пути. Таблицы для типов/ботов/причин хранятся один раз, время и ID можно кодировать дельтами. На границе блока (при имеющемся обмене процесса) передавать накопленные records в runner. Там записывать поток JSONL массивов с gzip и индекс match/round/episode; формат уже совместим с архивированием записей проекта. Если нужны большие корпуса, обучить компактный бинарный кодек на том же контракте только после измерения. Не клеить JSON в каждом тике, не использовать стеки для идентичности, не держать весь матч в объектном массиве, не сжимать в игровом тике.
4. **Два независимых буфера.** UI получает ограниченную выборку из полного потока и показывает «12 из N». Диагностический recorder держит ограниченный объём непереданных блоков. При заполнении приостанавливать только сценарий инструмента между батчами, никогда не использовать время записи как вход шага игры. Если экспорт невозможен, явно записать range пропущенных seq и причину, пометить прогон неполным и не применять как доказательство. Размеры блока и бюджеты — результат профилирования на целевой среде, здесь чисел нет.
5. **Снимок и воспроизводимость.** Manifest хранит SHA сборки, источник чисел, карту, seed, digest долгосрочного OPP и настроек, схему данных и детектора, частоту тика, предыдущие/следующие чанки, диапазон и хэш каждого, число dropped, поля/знаменатели и ссылки на имеющиеся checkpoint. Для контекстных эпизодов добавить ID ближайшего снимка и изолированный replay до события. Много эпизодов у одного чекпоинта делят один снимок. Хранение диагностического состояния отдельно от игрового снимка, за исключением явно требуемых метаданных воспроизведения.
6. **Приёмка.** Редьюсер заново вычисляет сумму всех `delta` и число возможностей из ledger. Результат обязан совпасть с сырым summary побайтно по числовым полям. Тесты с превышением старых лимитов и переносом чанка на новый раунд сохраняют каждый ID; повторы/порядок, отказ записи, усечённый архив, отсутствующий источник и неизвестная ревизия подсвечиваются как ошибки качества данных. Разбор любого инкремента возвращает конкретную причину и доказательство либо явно метку недостаточности контекста.

Нейтральность измерять при выключенном и включённом recorder на тех же входах, с остановленным кадром, сравнивать полное доступное состояние, события и память, а не только позиции. Отдельно измерить время тика, сериализацию, рост памяти и очередь на одинаковом корпусе. На базе есть доказательство для конкретного observer и прогона, но оно не распространяется на все monkey patch и Proxy (см. аудит).
