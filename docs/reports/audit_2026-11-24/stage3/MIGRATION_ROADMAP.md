# MIGRATION_ROADMAP — последовательность перехода и критерии завершения

Этап 3, 24.11.2026. Решение — `TECHNOLOGY_DECISION.md`; устройство — `FINAL_ARCHITECTURE.md`; по файлам — `MIGRATION_MATRIX.md`;
скорость — `PERFORMANCE_PLAN.md`; защита — `REGRESSION_PROTECTION.md`. Оценки объёма — в рабочих сессиях, как в `rebuild/PLAN.md`
(оценка, не обещание).

## 1. Выбор стратегии

| | **A. Постепенная перестройка** (рекомендуется) | B. Новое чистое ядро + перенос механик | C. Полное переписывание |
|---|---|---|---|
| объём | ~20–30 сессий R0–R5 (оценка по объёму матрицы) | ~40–60 (ядро + перенос 106 механик + сверка) | > 80; повтор месяцев работы |
| повторная реализация механик | нет: код переносится как есть, меняется граница | частично: каждая механика переносится в новое ядро и сверяется | все |
| риск потери поведения | низкий: каждый шаг — отпечаток бит в бит или сцена A/B | средний: сверка двух реализаций по отпечатку невозможна (другой порядок вычислений, `hypot` — `bench/exact.js`) | высокий: 1734 пометки решений, 555 со словами владельца, живут в коде |
| риск новых системных ошибок | низкий, ограничен шагом | средний | высокий |
| постепенность | да, по каналу | частично (две системы рядом месяцами) | нет |
| старое и новое параллельно | да: каждый шаг — версия, откат — `git revert` | да, но расходятся по битам | нет |
| автоматическое сравнение | **бит в бит** (отпечаток уже есть) | только статистикой | только статистикой |
| сопровождение потом | хорошее (типы + проверки) | хорошее | хорошее, если доживёт |
| возврат к развитию игры | после R0–R2 (скорость — R4, параллельно с развитием) | после переноса всего | через месяцы |

**Почему не B и не C:** главная ценность проекта — накопленное поведение (1734 решения в коде, демки, данные карт), а главный дефект —
устройство границ, которое чинится на месте. Перестройка 15–17.11 уже показала, что крупный перенос (21 модуль) возможен **бит в бит**
(прогон 271); «новое ядро» отказывается от этой проверки. Замер `bench/exact.js` показывает конкретный механизм потери: даже одна и та же
формула в другом языке даёт другие биты в 13 % запросов пути.

## 2. Правила, общие для всех этапов

1. **Не смешивать** в одной версии: перенос / архитектуру (бит в бит), смену языка (бит в бит), скорость (бит в бит, если возможно),
   поведение (сцены A/B + 8 матчей). Версия с буквой (`v6xxa`) — один вид работ.
2. **Старое не удаляется**, пока новое не прошло проверки этапа; переходник (старое имя зовёт новое) живёт до конца этапа.
3. **Откат этапа** — `git revert` версий этапа; каждый этап начинается с базы (отпечатки, сцены, замеры), с которой сравнивается.
4. **Отметки и снимки** сохраняются: формат снимка получает поле версии (R0); старые снимки читаются переходником, пока нужны.
5. **Rust (R6)** — только если этап R4 не дал нужного запаса; с общим набором математики (только `+ − × ÷ √`, свои `atan2/sin/cos` в обоих
   языках или вызов из JS), с тем же порядком обхода и правилами равенства, сравнение бит в бит на реальных запросах.

### R5. Исправления поведения по реестру (постоянно, по одному)

Каждое — отдельная версия: сцена A/B в реестре → правка у хозяина → L1 → 8 матчей → `fixed`. Первые (по `../SYSTEMIC_ERRORS_AUDIT.md` и
`../stage2b/UNKNOWN_DEFECTS.md`): П-01 (ключ подсказки), Б-3 (фетч — **ответ владельца**), У-2 (страница = замер — **ответ владельца**: какой
путь «нового матча» правильный), У-4 (`botRand`), У-6 (`Angle` в 370), П-03 (4 места `nadeTaskEnd`), У-7 (высоты в `hasLOS` — по одному
решению за раз), С-5 (`timeTo` с шагом и оружием), Б-1 (после раскадровки). Это уже **развитие игры**, не перестройка.

### R6. Rust-ядра — только по замеру (опция)

Условие входа — `TECHNOLOGY_DECISION` §5. Одно крейт-ядро (`route`, `ray`), WASM в Worker, N-API в Node; данные графа — один раз,
запрос — числа; сравнение бит в бит на 3000+ реальных запросах (как `bench/exact2.js`) и отпечаток матчей; JS-реализация остаётся
эталоном и запасным путём.

## 4. Когда перестройка закончена (измеримые критерии)

Перестройку прекращаем, когда выполнено всё ниже. Отсутствия игровых ошибок **не** требуется.

| # | критерий | как измеряется |
|---|---|---|
| 1 | у каждого поля бота, которое пишется в живом тике (сейчас 357), — хозяин в `owners.json` с `enforce` | `gen_maps.js --check`: 0 записей мимо хозяина |
| 2 | решения не читают истинное состояние врага | проверка сборки: 0; метаморфный тест знания на 50 снимках — 0 изменений решений |
| 3 | слои решений, знания, арбитража, исполнения — TypeScript `strict` | `tsc --noEmit`: 0 ошибок |
| 4 | копий общих правил вне `dmath` нет | детектор копий: 0 (угол, этаж, зерно, «конец гранаты», время до точки) |
| 5 | каждая подтверждённая находка этапов 1/2B — сцена в реестре (`confirmed` или `fixed`) | реестр: все П-, Б-, У- с номером сцены |
| 6 | L0+L1 идут на каждый коммит и укладываются в ~5 минут в облаке | время прогона |
| 7 | снимок в новой странице = игра; новый матч на странице = свежий матч | I-23, I-22 проходят |
| 8 | интерфейс не замерзает от симуляции | `frame_prof.js`: 0 кадров > 50 мс по вине симуляции |
| 9 | нет известных фризов | окна Р-01…Р-06: тик ≤ 62,5 мс; p99 не хуже базы R0 на ПК |
| 10 | анализ влияния правки работает | для изменённого файла выдаёт задетые механики, сцены, связки К-1…К-13 |
| 11 | новая карта проходит общий набор | `map_check.py` + общие сцены карты + 2 матча без нарушений инвариантов |
| 12 | Node-прогон = браузерный | отпечаток бит в бит |

Критерии 1–8 и 10 — «устройство»; 9, 11, 12 — «работает». После 1–12: обычная работа идёт по `REGRESSION_PROTECTION` §2–§4 — ошибка →
сцена (`confirmed`) → правка у хозяина → сцена `fixed` → L1 → публикация; влияние на соседей видно в отчёте анализа влияния.

## 5. Остающиеся риски

- **Перенос «бит в бит» может не получиться для отдельного шага** (порядок обхода, кэш). Тогда шаг делится или становится шагом поведения со
  статистикой (8 / 16 матчей) — медленнее, но видно.
- **Типы ловят не всё**: логика «что лучше сделать» остаётся задачей сцен и наблюдения владельца.
- **Ответы владельца** нужны для поведенческих шагов (Б-3, У-2 и др.) — без них R5 по этим пунктам стоит.
- **Объём** — оценка; R2 — самый длинный этап, он идёт по каналу и прерывается без вреда (каждый канал завершён сам по себе).
- **Скорость на ПК владельца** не измерена этим этапом — цели по мс назначаются после базы R0.
