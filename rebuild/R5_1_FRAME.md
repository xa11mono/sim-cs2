## Прогон 332: фактическая параллельность (разбор 26.11, владелец: «раннер работает с par=1 при 7–8 ГБ свободных»)
Причина — сторож `tools/measure/procguard.py` (до v637a), схема та же, что в журналах 329–331 (`pc-results/<N>/run.log`): Chromium par 8
на Ancient — матчи растут с ~0,6 до ~2 ГБ, допуск смотрел только на «свободно сейчас» → стартовали все 8, память кончалась, сторож снимал
самые новые матчи и резал `cap` 8 → 7 → 6 → 5 → 4 (обратно не поднимал), затем повтор снятых ставил `cap = 1` — до конца пула. В 331
очередь Mirage уже стояла в пуле и ушла с `cap` 4; в 332 фазы (`"phase": true`) идут через один пул по очереди — **все фазы после
первой многоматчевой (Chromium Ancient) шли с `cap = 1`**. Строки журнала 332 — после публикации `pc-results/332` (идущее задание GitHub
журнал не отдаёт); проверить: `guard: мало памяти`, `переигровка снятых`, `par ≤ 1`.
Следствие: отпечатки 332 годны (параллельность не влияет на игру); **сравнение массовой производительности Node и Chromium по 332
некорректно для par 8** — фактически шёл один матч. Исправлено в v637a (тест `tools/measure/procguard_test.py`): допуск по прогнозу пика
(«движок:карта», наибольший замеченный), постепенное восстановление `cap` до `par`, повтор снятых — по одному без снижения `cap`,
конец фазы возвращает `cap` к `par`; фактическая параллельность — `guard_<m>.json` (`par_seen_max`, `par_seen_avg`) и `phase.json`
(`par_max`, `par_avg`, `cap_log`). Замер параллельных матчей — повторить новым сторожем; готовые отпечатки не пересчитывать.

## Сторож: «при 5,5 ГБ свободно идут 2 матча Node, в очереди 3» (разбор 26.11, прогон 334 не трогался)
Допуск следующего матча (логика Codex, не менялась): (1) свободно − рост идущих до своего пика − пик нового ≥ запас (3195 МБ = 20 % RAM);
(2) общий лимит commit (Job Object): пики идущих + пик нового ≤ лимит (лимит = свободно − запас на момент создания; растёт, только когда
свободно − запас > лимита). Оба условия означают одно: **если все идущие и новый одновременно дойдут до пика, свободно останется ≥ запаса**.
Пример по числам 332 для Node Ancient (пик 1892): 5,5 ГБ свободно + ~2,6 ГБ уже занято двумя идущими = 8,1 ГБ; три пика = 5,7 ГБ →
в худшем случае свободно 2,4 ГБ — ниже запаса 3,2 ГБ, но выше критического 1,5 ГБ: третий матч не допускается именно из-за запаса. Для
Node Mirage (пик 1090) третий матч при тех же 5,5 ГБ допускался бы — значит, либо идёт фаза Ancient, либо пик Mirage в этом задании вырос,
либо держит лимит commit; точная причина — новая строка журнала «недопуск …» (v637a, со следующего задания).
Вывод: защита не ошибочна, а консервативна по выбранному запасу (одновременный пик всех идущих + 20 % RAM). Ослаблять без доказательства
нельзя: в 329–332 при нехватке память опускалась до 1,1–1,4 ГБ свободных (снятия), в 323 ПК зависал. Что даст доказательство: по журналу
недопусков и `guard_<m>.json` (пик, время пика) — совпадают ли пики одновременно идущих матчей; если нет — можно учитывать время до пика,
а не сумму пиков (решение — после данных).

## Р5.1 шаг 2 и Р5.2 (26.11, ветка v638a)
- **Кадр** `frameMake()` / `frameApply(F)` (`src/snapshot.js`): снимок только переменных, которые читает показ и меняет симуляция
  (`FRAME_VARS` — из `rebuild/gen/frame.json`: прямые чтения + косвенные через функции симуляции, которые вызывает сам рисунок `draw` /
  `d3Frame` (`readsVia`), без неизменяемых и настроек; 72 переменные), со ссылками на неизменяемые данные, граф зон — по `NAV_UNLINKED`,
  поля-кэши в неизменяемых данных. Проверка `tools/page/frame_apply_check.js`: страница без своей симуляции рисует из кадра попиксельно то
  же — Mirage м3, тики 3000 / 9000 / 20000 / 40000, все слои. Найдено по ходу: неполный кадр давали косвенные чтения (слои знания /
  «простреливается» вызывают функции симуляции) и поля-кэши рёбер графа.
- **Worker** (`src/build.py --worker`, страница с `?worker=1`): ядро той же карты (`tools/node/core_build.py`) — текстом в странице
  (`#simCore`), Worker из Blob-URL (`data:` на страницах-артефактах запрещён, Р0.2); страница шлёт «прошло ms» и свои часы показа `nowTs`,
  Worker крутит те же часы (`clockAcc` / `stepTick`) и отвечает кадром; страница кладёт кадр (`frameApply`) и рисует тем же кодом. Проверка
  `tools/page/worker_check.js`: попиксельно равно обычной странице — Mirage м3, тики 3000 / 9000 / 20000, со слоями и без.
  Найдено по ходу: симуляция метит эффекты показа временем страницы `nowTs` (круги звука, трассеры) — часы передаются с командой; строки
  войса и надпись смены сторон симуляция писала только при `document` — теперь флаг `SIM_SHOW` (страница и Node — как было, Worker
  страницы — включён).
- **Пока не в Worker:** разминка, песочница, повтор клатча, редакторы карты, отметки (снимок / перемотка) — в режиме Worker не включены
  (команды к ядру — следующий шаг); размер кадра (9–17 МБ текстом со всеми слоями) и частота — Р6 (решение владельца 26.11).
