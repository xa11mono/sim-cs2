# REGRESSION_PROTECTION — система предотвращения повторных ошибок

Этап 3, 24.11.2026. Классы ошибок — из этапов 1 и 2B; инварианты I-01…I-32 — `../TEST_COVERAGE_PLAN.md` §2.2, `../stage2b/*` §тесты;
устройство — `FINAL_ARCHITECTURE.md`; порядок внедрения — `MIGRATION_ROADMAP.md`.

Принцип: **каждый класс ошибки закрывается механизмом, который срабатывает на всех местах класса, а не на исправленном эпизоде.**
Порядок силы: (1) не скомпилируется (тип), (2) сборка падает (проверка устройства), (3) падает быстрый тест (инвариант / сцена),
(4) видно в статистике (8 матчей). Чем раньше ловится, тем лучше; статистика — последний рубеж, не основной.

## 2. Статусы поведения — что защищаем и что нет

Каждая сцена в реестре регрессий (`rebuild/scenarios.json`, расширенный формат) имеет статус:

| статус | смысл | как ведёт себя проверка |
|---|---|---|
| `preserve` | правильное поведение, которое нужно сохранить (набор B) | FAIL — регрессия, блокирует |
| `fixed` | исправленная ошибка (набор A) | FAIL — регрессия, блокирует |
| `known` | известный недостаток, пока допускается | не блокирует; изменение исхода — в отчёт («стало лучше / хуже») |
| `confirmed` | подтверждённая ошибка, ждёт исправления | ожидаемый FAIL; если вдруг PASS — в отчёт (исправилось побочно — проверить) |
| `unexplored` | ситуация не разобрана | только запись |

**Нельзя** записывать текущее поведение как `preserve`, если оно не подтверждено владельцем или источником (CLAUDE.md §6). Для **чистого
переноса** (рефакторинг, TS, скорость) эталон — отпечаток бит в бит старой версии; для **изменения поведения** — свойства из сцены A/B.

Формат записи (расширение существующего `rebuild/scenarios.json`):
```
{ "id": "R-03-fetch-cover", "status": "confirmed", "map": "mirage",
  "state": {"freshMatch": 3, "tick": 32600} | {"snap": "tools/marks/snaps/…json.gz"},
  "steps": 900, "assert": "через 8 с: бомба поднята ИЛИ сборщик идёт к ней ИЛИ прикрывающий ≤ 350 px",
  "preserve": ["R-03b: прикрытие работает, когда прикрывающий свободен"],
  "invariants": ["I-06","I-07","I-19"], "mechanics": ["M52","M30","M58"], "source": "SYSTEMIC_ERRORS Б-3" }
```

**Как исправление становится защитой автоматически:** правка поведения не принимается, пока не добавлена (или не переведена из
`confirmed` в `fixed`) её сцена с набором B. Проверка сборки сравнивает: в коммите есть правка файла решений/арбитража — должна измениться
запись реестра регрессий (иначе предупреждение; после R5 — ошибка).

## 4. Анализ влияния изменения (что проверять)

Из графа `an.js` (этап 1: функции, вызовы, запись/чтение полей) и реестра механик:
1. изменённые функции → механики (M-номера) → поля и переменные, которые они пишут;
2. → механики, которые эти поля читают (`../MECHANICS_INVENTORY.md`, «Зависят от неё»);
3. → сцены реестра с этими механиками + инварианты на эти поля + критические связки К-1…К-13 (`../TEST_COVERAGE_PLAN.md` §4).
Отчёт к правке: «изменено: M112; задеты: M30 (пост lineup), M118 (EXU), M117; сцены: R-01, R-02, …; связки: К-1, К-6». Это и есть
«закономерное влияние на другую механику — обнаружено и объяснено».

## 5. Регрессия или шум

| вид проверки | решение |
|---|---|
| отпечаток (перенос) | бит в бит или нет — шума нет |
| сцена A/B | детерминирована — шума нет; FAIL = регрессия |
| инвариант | число нарушений на одних и тех же тиках — детерминировано; рост = регрессия |
| статистика 8 матчей | только через `noise.py` (пороги CLAUDE.md §8: ≈ 10 % гранаты, 15 % stall, 20 % nav/tug/danger); ниже порога — «в шуме», не основание; для спорного — 16 матчей или переигровка тех же раундов (`replay_cmp.py`, пары раундов) |
| скорость | одинаковые тики, одинаковые матчи; среднее и p99; разница < 5 % — шум измерения (облако), на ПК — по повтору |
