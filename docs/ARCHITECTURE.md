> `mkpub.py` пишет страницу целым документом (`<!doctype html>` + обёртка из `000_head.html`).
Игра — один `<script>` (внутри обёртки `(function(){ … })();`) плюс разметка и стили вокруг, но лежит не одним файлом, а
кусками в `src/game/`: `000_head.html`, `002_style.html`, `004_markup.html` (до `<script>` включительно), код
`010_map_zones_warp.js` … `680_sound_frame_buttons.js`, `990_tail.html` (`</script>` и конец страницы).
- **Как собирается.** `src/gamesrc.py` → `game_source()` склеивает все `src/game/*.html|js` в порядке имён — это ровно
  прежний `src/game.html`. Его вызывают `src/build.py` (`sim.html`) и `src/mkpub.py` (`<карта>-radar.html`); других
  читателей исходника нет — инструменты (`health.py`, `measure/*`, `mark_open.js`, `replay_owner.js`, `map_shot.js`) берут
  собранный `sim.html`. Склейка одним файлом (для grep/diff) — `python3 src/gamesrc.py файл`.
- **Порядок важен.** Номер впереди имени — место куска в странице. Кусок кода — не самостоятельный файл: первый открывает
  обёртку, последний закрывает. Номера идут с шагом 10, новый файл — номером между соседями (например `175_…js`).
- **Всё видно везде.** Все `var` и `function` — в одной области видимости (обёртки): функцию из одного файла можно звать из
  любого другого, объявления функций поднимаются. Но **числа и объекты при загрузке** (`var X = …`, вызовы верхнего уровня)
  выполняются по порядку файлов: `var`, который при загрузке читает другой `var`, должен стоять в файле с большим номером
  (или ниже в том же файле) — так же, как раньше было «ниже по строкам».
- **Правка механики — в её файле** (таблица «Где что» — в CLAUDE.md); новую функцию класть в файл своей механики; файл
  больше ~600 строк — делить по границе функций (неделимые пока: `tBrain`, `draw`, `ctBrain`, `stepTick`).

## Набор карты (v317, этап 1 из 3 подготовки к 7 картам; v318 — сборка из исходников)

Всё, что относится к одной карте, лежит в `data/maps/<карта>/`. Код `src/game.html` карт не знает: в нём нет ни названий
мест, ни координат, ни тактик, ни радара — только объект `MAP`. Сборка вшивает набор выбранной карты:
`python3 src/build.py [--map ancient]` → `sim.html`, `python3 src/mkpub.py [--map ancient]` → `<карта>-radar.html`

остаются ровно как записаны (в высотах и местах про есть `-0`, `JSON.stringify` превратил бы его в `0`).

## Карта 3D (map3d.json) — А3–А4 (20.10.2026), в игре с А5
Источник — геометрия столкновений из файла игры (`data/maps/<карта>/geom3d/world_physics.npz`, А1–А2), без невидимых стен
и без «стен радара». Сборка: `python3 tools/map3d/columns.py --map <карта>` (≈ 80 с) → `layers.py` (≈ 35 с) → `zones_owner.py`;
картинки — `layer_pics.py`; проверка образцом игры — `node tools/map3d/map3d_check.js <карта>`. `map3d.json` (с А5) — в корне набора
(игра: `MAP.map3d`); остальное — в `geom3d/` (в `MAP` не попадает: `src/mapset.py` берёт только `*.json` в корне).

**В игре (А5)** — `src/game/035_map3d.js` (один код с node: `tools/map3d/map3d.js` его подключает): распаковка zlib своя
(`zInflate`, синхронно, ≈ 0,25 с на загрузку), `m3()` — геометрия при первом вопросе; столбики гранат и неба — при первом
броске. Что берёт геометрию, если она у карты есть (иначе — прежняя сетка VIS по стенам радара, навмешу и укрытиям; с А6 геометрия есть и у Ancient — у обеих карт):
- `visMarch` = луч `m3Line(…, 'sight')`; `visWallHit` и `levelBlocked` — пусто (у геометрии свои стены и перекрытия на каждом этаже);
  `visFloorAt(x, y, z)` — этаж клетки на высоте бота (самый высокий не выше z + 18), без z — верхний этаж «пешком». `visParts` —
  голова, грудь, живот, плечи ±14 ед. (М140) — через них; `hasLOS(x1, y1, x2, y2, z1, z2)` — с высотой бота (М140);
- `insideSolidWall` / `segCrossesManualWalls` / `crossesWall` / `nadeWallHit` — по сетке `m3Solid` (клетка без этажа геометрии и без
  навмеша; кто уже «в стене», выходит); `rebuildNav` участки не выкидывает и переходы не режет — ходьба по навмешу из того же файла;
- `nadeArc` — дуга ломаной из 12 лучей `'nade'`, `nadeCovered` — над полом есть преграда для гранат выше 80 ед. (временно, до В2–В3);
- стены радара (`walls.json`, `MANUAL_WALLS`) — рисование, редактор и лучи «конуса» на экране; укрытия, высоты, крыши набора
  видимость не читает. Проверка «кто кого видит» (`610`) красит клетки, где есть этаж «пешком».

**Большая карта (А6, Ancient):** у `prims` поле `tri32` — номера вершин `Uint32`, `delta` — номера и вершины записаны разностями с
предыдущим (игра суммирует при загрузке); точная проверка — корзины 4 × 4 клетки и отсев треугольника по высоте отрезка.

**Сетка** — та же, что `VIS`: клетка `cell` = 2 px радара 0..2048 (`unit` = 5 ед. игры у Mirage), `W` = 1024 клетки по стороне,
клетка `(i, j)` = `x ∈ [i·cell, (i+1)·cell)`, `y` — так же; номер `j·W + i`. Все массивы — little-endian, сжаты zlib (deflate) и в base64
(в браузере — `DecompressionStream('deflate')` при загрузке, в node — `zlib.inflateSync`).

`geom3d/map3d.json` (≈ 2,1 МБ):
| поле | что | кто берёт |
|---|---|---|
| `sight` `{n, lo, hi, mat}` | столбики для **взгляда и пуль**: `n` (Uint8, на клетку) — сколько отрезков; `lo`/`hi` (Int16, ед. игры) — занятые высоты по порядку, подряд для всех клеток; `mat` (Uint8) — материал отрезка (номер в `mats`) | `VIS` (видимость), прострелы |
| `nade` `{n, lo, hi}` | то же для **гранат** (с grenadeclip, решётками, стеклом; без playerclip) | полёт гранат |
| `sky` `{n, lo, hi}`, `sky_z` | **небо** (skybox): столбики и низ потолка неба над клеткой (Int16, 32767 — нет) — граната отскакивает, взгляд и пули не замечают | гранаты |
| `floors` `{n, z, kind}` | **этажи**: в клетке `n` этажей, `z` — высота пола (по возрастанию), `kind` 1 — пешком (и по лестнице), 2 — только прыжком, 3 — только подсадкой | `visFloorAt` по высоте бота, зоны |
| `prims` | **точная геометрия**: вершины `v` (Int16 ×4 = 0,25 ед.), треугольники `tri` (Uint16 ×3), `tri_flag` (1 — взгляд, 2 — граната), `tri_mat`; выпуклые блоки — `hull_n` (плоскостей), `hull_p` (Float32 n·p ≤ d — внутри), `hull_box`, `hull_flag`, `hull_mat` | узкая проверка луча, нормаль для отскока |

**Луч** (`tools/map3d/map3d.js`, образец для игры: `m3Load`, `m3Line`, `m3Hit`, `m3Floors`, `m3FloorAt`): 1) идём по клеткам линии
(как `visWallHit`), в каждой — высота линии от входа до выхода против отрезков клетки; ни одного пересечения — **свободно**
(столбики пишутся с запасом: геометрия, задевшая клетку краем, занимает её целиком, — так что «свободно» всегда верно);
2) пересечение — точная проверка треугольников и блоков из «корзины» 16×16 клеток против всего отрезка. Ответ совпадает с лучом по
треугольникам А1 (закрыто 0,7 % / стоя 6,0 % убийств про), ≈ 8 мкс на луч. `m3Hit(…, 'nade')` даёт первое попадание с нормалью и
материалом — для отскока гранаты от пола, ступеней, стен, крыш; небо — отдельной проверкой по `sky`.

`geom3d/zones_owner.json` (А4): `zones[]` — `name` (как у игроков, по подписям владельца), `role` (`Asite`/`Bsite`/`CTspawn`/`Tspawn`),
`level` (`low` — нижний этаж: Underpath), `z` (мин / медиана / макс пола), `rects` (ровные прямоугольники зоны, px радара 0..2048),
`owner_rects` (прямоугольники владельца), `center`; `floor_zone` (Uint8 на каждый этаж `floors`, тот же порядок; номер в
`floor_zone_names`) — зона точки = зона её этажа (клетка + высота), так зоны верно делят Underpath и Short над ним.
Слои для картинок и проверок (`layers.npz`, не в репо): стены, укрытия с верхом, окна, проёмы, крыши, подъёмы — определения в
`tools/map3d/layers.py` (шапка) и `docs/reports/MAP3D.md`, «А3».

## Арбитр места (v378, М126 этап 6)
Одно место выбора задачи для позиции бота — `setPost` (`110_post_routes.js`). Канал только один — место; взгляд, гранаты,
стрельба — свои решения.
- **Таблица важности** `TASK_LEVEL` (проектный порядок, сверху важнее; по началу tag задачи):
  11 бомба (flee, defuse, stopplant, antidefuse, plantspot) → 10 выжить (save) → 9 бой (contact, tradeR, repos:killmove) →
  8 ретейк / сбор / ротация на колл (retake*, gather*, rotate, rotate:bomb, bombwatch, postplant*, fetch) → 7 эндгейм и клатч
  (endhunt, hunt, clutch) → 6 перестановки в бою (остальные repos:*) → 5 команда (fill, rotateHold, fetchCover, bombEscort,
  bombWait, coverplant) → 4 гранаты и ожидания (lineup, smokeWait, utilWait, utilHold) → 3 личные перестановки (pickup,
  probe*, rebal*, shift, earlyPeek, midcover) → 2 маршрут (route:*) → 1 пост роли (всё остальное). Роль и ситуация в таблицу не
  входят — они только порождают задачи.
- **Правило перебивания** (`taskCanSet`, его же применяет `setPost`): текущая задача бота — `b._task` (уровень, начало tag,
  когда началась, когда подтверждена). Новая задача: выше — ставится сразу; того же уровня — не раньше `POST_DWELL` (1,5 с) после
  смены; ниже — только когда текущая кончилась (механика сама сняла её — `clearPost`) или устарела (не подтверждалась
  `TASK_STALE` = POST_DWELL; подтверждение — `setPost` того же tag или `postKeep`). Задачи, которые ставятся один раз, живут
  своим сроком (`taskKeepUntil`: контакт — CONTACT_HOLD, размен — окно 3,5 с, подмена — до 15 с / пока план не сдвинулся,
  перестановка — `_reposUntil`, ребаланс — до конца раунда). Одна задача — одинаковое начало tag (до «:»/«|»), кроме repos:* —
  каждая перестановка своя.
- **Маршрут раша** — путь к посту роли: пост роли становится его концом; задача уровня 8+ (и у CT поставленная бомба)
  маршрут снимает, задачи 3–7 — пауза маршрута.
- **Отказ** — `setPost` возвращает false, и механика делает своё сама: лайнап — бросок отменён; ожидание у смока — снято;
  подбор — помнит предмет (`_pickGo`) и возвращается, когда задача важнее кончилась; размен / подмена / ребаланс — не начинаются
  (без войса). Механики, которые решают, затевать ли своё, спрашивают `taskCanSet` (откат, добить, перестановки после фрага,
  подбор, ожидание у смока), а не свои списки tag.
- Замков со своими списками (`_egLock`, `_pickLock`, `_smokeWaitLock`, `_lineupLock`, `POST_URGENT`, проверки `_contact.lock`,
  `_tradeLock`, `_fillLock`, `_rebal`, `_probeLock`, `_reposUntil` в `setPost`) больше нет.

## Арбитр взгляда (v381, М126 шаг 4)
Одно место выбора, куда смотрит бот: `lookArbiter` (`270_look_plan_smooth.js`), вызывается из `resolveEngagements` (враг виден —
верхний уровень, это решается там же). Канал только взгляд: место, гранаты, стрельба (`tryShoot` целится в видимое сам) — свои решения.
- **Кандидаты** `{уровень, вид, точка, вес}` — механики только предлагают; источники — только то, что бот знает: свои уши
  (`heardSound`), радар и войс (`beliefLast`), киллфид (`teamIntel.sig` «died»), свой контакт (`_contact`). Роль и ситуация в таблицу
  не входят — они порождают кандидатов (роумер — точка проверки, фейк-дефуз — вход T, точка про — её угол, пост — свой угол).
- **Таблица важности** `LOOK_LEVEL` (проектный порядок, сверху важнее): 12 враг виден → 11 бой (свой контакт ≤ 1 с `lookContactFresh`,
  спам в смок `_spam`, тиммейт попросил второй угол `_coverDir`) → 10 свои уши ≤ 1 с и смерть тиммейта рядом ≤ 3 с → 9 команда знает
  сейчас (≤ 1 с) → 7 мой угол: поручен задачей (роум-чек, фейк, точка про на посту) или выдан делёжом команды (`lookPlan`) → 6 угол по
  пути (`prePeekTick`, `_pie`) → 4 угол поста. Внутри уровня — больший вес (`LOOK.contactW` × близость × свежесть, для «боя»: контакт >
  спам > второй угол). Точка на знание — `lookKnowPt` (где враг выйдет на линию, `holdRelevant`, на бегу за спину — только свежее и
  близкое, путь закрыт своим — не кандидат).
- **Последняя позиция врага (1–8 с) и контакт старше 1 с** — не отдельный уровень, а веса внутри дележа (`lookCands`): иначе взгляд
  залипал на них и не чередовался с открытыми углами (v375).
- **Командный делёж** `lookPlan` (раз в 8 тиков) — без изменений: зоны, входы, позиции из демок, «как у про», угол поста, путь к
  известному врагу; выдаёт кандидата уровня 7 («мой угол»). Свежее ≤ 1 с в делёж не входит — оно выше.
- **Общий шаг после выбора** `lookFilter`: не в спину своему (уровни ≤ 7 → `openDirLook`), не в стену (`openLook`, `flatWallAhead`),
  плавность (`smoothLookFilter`, срочность `lookUrgent`: бой — 2, уши/команда — 1). Бросок гранаты — смотрит туда, куда кинул.
- Разбор взгляда (`lookDbgPanel`) показывает кандидатов арбитра по уровням (`_ldArb`).
- Удалено (v381): мёртвая цепочка «если… иначе» в `resolveEngagements` (при `BAL.newLook` она не работала), `threatLook`, `deathLook`,
  `saveLook`, `beliefLook`, `smokeSweepLook`, `mateAhead`, `newLookFor`; переключатели `newLook`, `smoothLook`, `noWallStare`,
