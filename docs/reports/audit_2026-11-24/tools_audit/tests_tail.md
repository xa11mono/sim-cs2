## 5. Регрессионный набор этого аудита (сцены с фиксированным состоянием)

Состояние до T0 можно один раз сохранить снимком (`tools/marks/snap_round.js`), чтобы не доигрывать 30 000 тиков каждый раз: в облаке это

## 6. Что записывать во время симуляции

Только запись, игра не меняется (как `rec2.js`). Проверка — отпечаток бит в бит с записью и без неё.

1. **Время по этапам тика** S1–S9 (9 отметок `performance.now`); для тиков > 50 мс — ещё бот и механика (задание гранаты, `nadeThrowSpot`,
   первый тик раунда). Раздельно по картам.
2. **Каждая попытка броска:** бот, тип, итог, причина отказа (`NADE_FAIL`), число подборов, мс, ключ подсказки (П-01, П-04).
3. **Каждый `setPost`:** механика (вызывающая функция), тег, уровень, итог, чем занят (если отказ). Сейчас это уже пишет `dlog`, но только
   текстом, и сторож разбирает текст.
4. **Все писатели скорости за тик** (а не только `_stopWhy`): `moveSpeedTick` / `_fc` / поворот / огонь / лестница / стрейф.
5. **Точка поста** раз в 0,5 с (в `act` сейчас только тег), чтобы отличить разворот решения от застревания (Н-01).
6. **Путь:** длина, индекс, сбросы детекторами с причиной (`stuckTicks`, `_netStuck`, прогресс, вне пола, уступ), `z`, участок навмеша.
7. **Командные ожидания:** `fetchId`, `fetchCover`, сборщик → бомба, прикрывающий → сборщик; ожидание выхода T (`exuGate` — `why`, `eta`).
8. **Нарушения инвариантов I-01…I-18** — эпизодами (матч, тик, бот, значение).
9. **Выстрелы в одном тике:** пары, где оба готовы стрелять (`fireReady == 0`) — кто выстрелил первым и попал (О-02).

## 7. Протокол «до / после» для одной правки

1. **Зафиксировать базу:** сборка базы (коммит), её отпечатки матчей 3, 7, 11 (`fingerprint.sh`), сцены L2 этой механики и связок (§4) —
   результат каждой (ok/FAIL + числа), окна скорости (§5) — мс.
2. **Правка** — у хозяина решения (CLAUDE.md §7).
3. **Если правка не должна менять игру** (перенос, скорость, диагностика): отпечатки бит в бит. Иначе откат.
4. **Если меняет:** сцены набора A — ok; сцены набора B — как в базе; инварианты L1 на 2 матчах в облаке — нарушений не больше, чем в базе;
   окна скорости — не хуже. Затем L3 (переигровка раундов) и L4 (8 матчей) на ПК.
5. **Отчёт:** таблица «сцена — база — правка», список нарушений инвариантов «было / стало», окна скорости «было / стало».

### Этапы построения системы тестов

| этап | что сделать | зачем первым |
|---|---|---|
| **T0** | перепроверить `tools/measure/audit/scenarios*.js`: каждую сцену — починить, переписать под текущее поведение (с владельцем) или удалить; запустить `rebuild/scenarios.json` | сейчас FAIL ничего не значит (Т-01) |
| **T1** | наблюдатель инвариантов I-01…I-18 (один файл в `tools/measure/`, только читает) + время по этапам (I-13) | дёшево; сразу даёт эпизоды по всем механикам |
| **T2** | сцены Р-01…Р-08 как JSON-строки в `rebuild/scenarios.json` (формат уже есть: `pre`, `tick`, `steps`, `ask`) + автоматическое утверждение | регрессия находок этого аудита |
| **T3** | проверки сборки §2.1 (таблица задач, замки, пары полей, `setPost` без результата — сначала предупреждения) | ловят класс ошибок до запуска |
| **T4** | сцены связок §4 (по одной на связку, A и B) | главный риск локальных правок |
| **T5** | матрица §3 — по мере правок: правишь механику — добавь её сцены | покрытие растёт с работой, а не отдельным проектом |

### Что можно автоматизировать, а что — нет

- **Автоматически:** L0, L1, L2 с числовым утверждением, L5, отпечатки, сравнение пар раундов (L3), статистика (L4).
- **Только владелец:** «выглядит ли как про» (видео «было / стало» — `tools/marks/mark_video.js`), как должно быть там, где владелец не расписал
  (наборы A/B для новых сцен), правильна ли таблица `TASK_LEVEL` (Н-04: «ротация не даёт кинуть лайнап 12 с» — решение, а не баг).
