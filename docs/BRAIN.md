## 0. Главный принцип → архитектурное ограничение

> Бот знает и делает то, что может знать и делать настоящий игрок в
> про-матче — не больше и не меньше. (docs/PRINCIPLES.md, главный принцип 06.10)

Технически: **у каждого бота есть приватное состояние знания (Knowledge), и
ни одна функция принятия решения не имеет доступа к истинному состоянию
мира — только к Knowledge этого бота.** Любая новая механика проверяется
вопросом «через что конкретно игрок мог бы это узнать» — иначе бот этого не
знает. Никаких правил под отдельные ситуации — поведение выводится из модели
восприятия, команды и ролей.

## 1. Источники информации (восприятие)

| Источник | Что даёт | Точность / задержка |
|---|---|---|
| Зрение (`10_vision.js`, уже есть) | Точная позиция, поза, оружие, эффекты (дым, флешка на экране) | Мгновенно, пока в FOV и видимости |
| Звук шагов | Направление + грубая дистанция, не точка; зависит от шаг/бег/крадучись и материала пола | Задержка минимальна, неточность по позиции |
| Звук выстрела | Направление + оружие | Мгновенно, дальность больше, чем у шагов |
| Звук гранаты | Направление броска (если был рядом/видел замах) и точка разрыва | Разрыв слышен почти по всей карте |
| Киллфид | Кто кого, чем, откуда (косвенно), сколько живых | Видят все, без задержки |
| Бомба | Заложена/обезврежена/тикает | Тиканье — ограниченный радиус от сайта |
| Тимспик | Всё, что сказал тиммейт | Задержка 0.5–2 с на произнесение, слышат все свои сразу после |
| Память | Последний контакт по каждому живому врагу | См. раздел 2 — не угасает линейно |
| Таймер раунда / фаза | Точно известно всегда | — |

## 2. Вера в позицию врага — гипотезы, не число

**Не делать**: `confidence: float`, линейно угасающий к нулю со временем. Это
даёт ложный эффект «через N секунд бот точно знает, что враг ушёл» — так
не бывает: враг мог и уйти, и остаться держать угол (бейт). Обе гипотезы
живут параллельно, время само по себе их не схлопывает.

```js
threatBelief[enemyId] = {
  lastConfirmed: { pos, tick, stance, source },   // последний точный контакт, неизменяемый факт
  hypotheses: [
    { type: 'held',          area: lastConfirmed.pos,  weight: 0.55 },
    { type: 'moved',         area: navAreaA, weight: 0.15, viaPath: [...] },
    { type: 'moved',         area: navAreaB, weight: 0.10, viaPath: [...] },
    { type: 'moved_unknown', area: null,     weight: 0.20 },
  ] // сумма весов = 1
}
```

**Порождение `moved`-гипотез**: от `lastConfirmed.pos` по навмешу — все пути,
куда враг физически мог дойти за прошедшее время (по скорости шаг/бег/крадучись;
если шагов не было слышно — крадущийся вариант не исключается). Вес пути — не
геометрия, а тактический смысл: ведёт туда, где враг полезнее команде — выше;
должен был быть слышен на этом отрезке, а звука не было — ниже; подтверждён
другим источником — резкий рост, остальное режется.

**Обновление — только событием, не тиком**: новый контакт/звук → пересчёт
весов причастных путей; истекло окно «должно было быть слышно на этом пути» →
лёгкое ослабление конкретной ветки, не всей гипотезы; киллфид/урон/счёт
живых → сильные прямые обновления; очень долгое молчание по всей карте →
рост `moved_unknown` (мог пройти куда угодно), а не исчезновение `held`.

**Использование**: прицел распределяется по весам (в первую очередь —
`held`), но боты по сюжету эпизодически перепроверяют весомые `moved`-точки
(это и есть «возвращаться проверить угол, который вроде пустой»). Решение
«идти проверять / держать» — по ожидаемой стоимости ошибки каждой гипотезы,
не по пороговому значению.

## 3. Командная картина и войс

```js
teamKnowledge = {
  threats: Map<enemyId, ThreatInfo>,              // объединение Knowledge своих: максимум веса/самый свежий источник по каждому врагу
  claimedPositions: Map<botId, {corner, since}>,
  openRequests: Map<requestId, {askerId, target, responders: Map<botId,'yes'|'no'|null>}>,
  planState: {type:'default'|'execute'|'retake'|'stack', site, declaredAt, activeSetupId},
}
```

Важно: слияние — это **то, что явно произнесено и услышано через очередь
войса**, а не мгновенный доступ к чужой Knowledge (иначе получится командная
телепатия).

Типы сообщений: инфа-колл, просьба, ответ на просьбу (без повторов — один
ответ на запрос, кто сказал «не могу» — не переспрашивают), план на старте
раунда (говорит только IGL), перестройка плана (триггер по условиям, раздел 5),
срочный крик (перебивает очередь). Очередь: несколько голосов одновременно —
последовательно, при 3+ не важное может быть не произнесено (реалистичный
разброс, не баг). Дедупликация по смыслу (то, что уже общеизвестно команде —
не произносить), актуальность по таймстампу (устаревшее не озвучивается).

## 4. Позиционирование — Setup, кроссфайр, роли (не зоны, не формула по краям)

Позиция у про почти никогда не выбирается индивидуально и покадрово — она
выбирается под тактическую задачу, парно/группой, и держится, пока задача не
меняется.

### 4.1. Setup — единица расстановки

```js
Setup = {
  id: 'ct_default_ancient', side: 'CT',
  slots: [
    { role:'anchor_A',  area:'Triangle', angle:'CaveEntrance', pairWith:'support_A' },
    { role:'support_A', area:'MainHall', angle:'Alley',        pairWith:'anchor_A' },
    { role:'anchor_B',  area:'Jungle',   angle:'DonutArea',    pairWith:null },
    { role:'mid_control', area:'MidTop', angle:'MidTunnel',    pairWith:null },
    { role:'igl_float', area:'variable', angle:'variable',     pairWith:null },
  ]
}
```

Бот встаёт в свой `slot` выбранного Setup'а и выполняет его `angle` — позиция
не пересчитывается заново каждый тик.

### 4.2. Кроссфайр

Пара `pairWith` стоит так, что их углы пересекаются на одном входе с разных
сторон: trade distance (достаточно близко для размена), ни один не виден
третьему направлению, пока враг не показался на их входе.

### 4.3. Standard vs off-angle

Standard — ожидаемая точка, хуже для соло-фрага, лучше для быстрого трейда
(anchor/support). Off-angle — неожиданная, больше шансов на пик без размена,
но изолирует бота (lurker/entry или adaptivно, когда standard уже «прочитан»
противником по ходу матча). У каждой area — набор именованных точек-кандидатов
с пометкой `standard`/`off`, slot в Setup задаёт предпочтительный тип.

### 4.4. Адаптация — read and react, не пересчёт на тик

Расстановка держится, пока не произошло: подтверждённая угроза (высоковесная
гипотеза направлена на slot → «подготовиться к контакту», не смена позиции),
команда меняет активный Setup целиком (раздел 5), угол временно бесполезен
(дым, фланг) → отход на запасную точку, которая тоже часть данных slot'а.

### 4.5. Данные карты

`mapPositions` — не вычисляются геометрией, задаются по ролям, источник —
демки про (standard/off, кроссфайр-пары, trade distance) как структурированные
данные, не как «небольшой бонус» к формуле:

```js
mapPositions.ancient.CT = [
  { id:'triangle_cave', area:'Triangle', type:'standard', angle:'CaveEntrance', crouch:true },
  { id:'jungle_offangle', area:'Jungle', type:'off', angle:'DonutArea', crouch:false },
]
```

## 5. Тактические режимы — переключение Setup'ов, утилита внутри сценария

Режим — не отдельная if-ветка поведения бота, а выбор **другого Setup
целиком**, со встроенной утилитой как последовательностью шагов с
зависимостями (не независимые решения каждого бота в моменте).

### 5.1. Execute (T)

```js
ExecuteSetup = {
  id:'execute_B_ancient_default', side:'T', site:'B',
  steps: [
    { actor:'support_smoke', action:'throw_smoke', target:'DonutFromMain', triggers:'round_start_plan_declared' },
    { actor:'support_flash', action:'throw_flash',  target:'BSiteOverDonut', dependsOn:{ afterSmokeLands:'support_smoke' } },
    { actor:'entry', action:'push', target:'BDonut', dependsOn:{ afterFlashPop:'support_flash', maxDelayTicks:20 } },
    { actor:'awp',   action:'hold_angle', target:'MainFromJungle', dependsOn:{ afterEntryCommitted:'entry' } },
    { actor:'lurker', action:'hold_flank', target:'MidTop' },
  ]
}
```

Бот не решает «кинуть гранату, потому что выгодно по формуле» — он исполняет
свой шаг по `dependsOn` (видит/слышит событие сам, как игрок) либо, если не в
сценарии (lurker), действует по независимой логике роли. Выбор конкретного
варианта execute — по плану IGL, по весу гипотезы (есть сильная инфа по углу —
берём вариант, у которого шаг режет именно его), по экономике, по паттерну
последних раундов.

### 5.2. Retake (CT)

```js
RetakeSetup = {
  id:'retake_A_ancient', side:'CT', site:'A',
  gather: { area:'MainHall', minPlayers:2, waitForTicks:40 },
  steps: [
    { actor:'util_1', action:'throw_smoke', target:'PlantCommonSpot', condition:'cutOffPlantSightline' },
    { actor:'util_2', action:'throw_flash', target:'SiteEntry', dependsOn:{ teamGatheredAt:'gather' } },
    { actor:'entry',  action:'push', target:'A', dependsOn:{ afterFlashPop:'util_2' } },
    { actor:'defuser_cover', action:'hold_angle', target:'rotationPathFromMid' },
  ],
  abortIf: { teamAliveBelow:2, bombTimerBelow: ticksNeededToEnter + ticksNeededToDefuse },
}
```

`gather` — не лезут поодиночке (размен невыгоден). `abortIf` — расчёт
«успеваем ли», по объективно известному таймеру бомбы; если нет — ретейк не
начинается, раунд может быть сдан без попытки (реальный паттерн про-команд).

### 5.3. Стак

Не отдельный механизм — вариант дефолтного Setup с другим распределением
slot'ов между сайтами (3 на A вместо 2), выбирается так же, как вариант
execute (инфа + паттерн раундов + экономика).

### 5.4. Переключение Setup'ов

`teamKnowledge.planState` — одно значение, меняется по явным триггерам:
бомба заложена → RetakeSetup; сильная инфа + колл IGL → execute/stack-вариант;
истёк контрольный тайминг без контакта → default → execute по умолчанию;
критическая потеря состава → упрощённый fallback. Переходы — редкие и
осмысленные, не пересчёт каждую секунду (постоянное дёргание между точками —
главный симптом старой системы, которого быть не должно).

## 6. Роли — атрибут на матч, модификатор систем выше

```js
RoleProfile = {
  entry:   { aggression:0.85, tradeReliance:'high_but_commits_anyway', infoIndependence:0.2, preferredAngle:'standard_or_deepest' },
  support: { aggression:0.45, tradeReliance:'high', infoIndependence:0.3, preferredAngle:'standard', clearsOffAngles:true },
  awp:     { aggression:0.3,  tradeReliance:'medium', infoIndependence:0.4, preferredAngle:'long_sightline', repositionAfterShot:true },
  lurker:  { aggression:0.5,  tradeReliance:'none', infoIndependence:0.9, actsOnOwnKnowledgeOnly:true },
  anchor:  { aggression:0.2,  tradeReliance:'needs_partner', infoIndependence:0.3, delaysRatherThanWins:true },
  igl:     { aggression:0.35, tradeReliance:'high', callsSetupSwitches:true, sacrificesForInfo:true },
}
```

`aggression` модулирует выбор между «пик/подпуш/джиггл» и «держать» (5).
`tradeReliance` — entry коммитится в сценарий даже без идеальной синхронизации
(мягкий `maxDelayTicks`), anchor/support не займут off-angle без партнёра.
`infoIndependence` — обычный бот доверяет колу тиммейта как своему зрению;
lurker (`actsOnOwnKnowledgeOnly`) может действовать по своей неподтверждённой
гипотезе один. `preferredAngle` — фильтр кандидатов при выборе точки (4.5).
IGL — не «играет лучше», а имеет право менять `planState` (5.4) и объявлять
план в начале раунда.

## 7. Бой и прицел — привязка к конкретной точке, не формула по тику

```js
engagementPrep(bot, enemy) = {
  crosshairOnExposurePoint: bool,  // прицел уже стоял там, где появился враг
  stanceReady: bool,
  source: 'setup_default' | 'prefire_from_info' | 'reactive_turn',
}

reactionTimeMs(bot, prep) =
    baseReaction(bot.skillTier)                    // 150–250 мс, разброс как у живых людей
  × (prep.crosshairOnExposurePoint ? 0.0 : 1.0)
  × (prep.source === 'reactive_turn' ? 1.4 : 1.0)   // неожиданный контакт — заметно медленнее
  × roleModifier(bot.role)
```

Прицел всегда нацелен на конкретную осмысленную точку: `angle` активного
slot'а (4), точку максимального веса гипотезы (2), либо точку, предписанную
шагом сценария (5) — никакой формулы «опасности краёв» по тику. Ширина
удержания угла широкая по умолчанию, сужается (префайр) при появлении
весомой гипотезы по конкретному входу. Исход контакта — не бросок кубика, а
кто раньше получил валидный прицел на уязвимую зону с учётом реального
времени реакции; дальше — существующая стрельба (С1: темп, отдача,
контрстрейф — не трогается, только источник цели прицела меняется).

## 8. Архитектура реализации

Не ML/RL — детерминированный, читаемый код (требование: воспроизводимость
`freshMatch(N)`, отпечаток «бит в бит» при правках движка, демки — только
источник данных/сверки, не обучение). Три техники:

1. **Utility AI** — потактовые решения бота (куда смотреть, где стоять в
   пределах роли/slot'а, вступать ли в бой): кандидаты → явная формула из
   понятных слагаемых → максимум. Объяснимо по логам.
2. **Скриптованные планы с зависимостями (HTN-лайт, без поиска)** —
   `ExecuteSetup`/`RetakeSetup`: конечный заранее написанный набор сценариев
   (`steps`+`dependsOn`), выбор варианта — Utility AI поверх небольшого числа
   вариантов.
3. **Лёгкий трекер гипотез** — `threatBelief` (2): 3–5 именованных гипотез с
   весами и правилами обновления по событиям, не байесовская сеть.
